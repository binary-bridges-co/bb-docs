bb-sign keeps each file of an envelope for the period of your organization's policy:
<Fact of={ORG_STORAGE.defaultRetentionDays} unit="days" /> with the standard configuration, or the
period your organization has agreed, from <Fact of={ORG_STORAGE.minRetentionDays} unit="days" /> to
<Fact of={ORG_STORAGE.maxRetentionYears} unit="years" />. This page explains how that period is
counted, what each envelope's **Retention** section shows, how to ask for a file that needs a restore
and how to keep every envelope in your organization's systems before the period ends.

## How long each file is kept

The period is counted separately for each file:

| File | The period counts from |
|---|---|
| **Original PDF** | When the document is uploaded. |
| **Signed PDF** | When the envelope completes. |
| Evidence certificate and audit trail | When the certificate is issued. |

When the period ends, the file stops being available and is permanently deleted in the following days;
after that it cannot be recovered. Files created before your organization had dedicated storage keep
the previous rule, <Fact of={ORG_STORAGE.legacyRetentionDays} unit="days" />. Each envelope's evidence
certificate states the period of its files. Your organization's policy, and how to request another, are
in [Storage and retention](/en/sign/admin/storage/).

## The envelope's Retention section

Each envelope page has a **Retention** section with the date from which its files can no longer be
downloaded:

> No longer available from \{date\}; it is then deleted permanently.

The date is the earliest across the envelope's files, at 00:00 UTC; the API gives each file's exact
date. Below it are a note and links to the [terms of service](/en/sign/legal/terms/) and to this page.

The section can also show an "Archived from \{date\}" line, which is not shown today. Before each
download, bb-sign checks the file's actual state: whether it needs a restore depends on the storage tier
it is in, not on a date.

An evidence certificate issued before the current version of bb-sign keeps the dates it was sealed
with, which can differ by one day from the ones the application shows today. The dates in the
application and the API are the ones in force.

## Archived envelopes and storage tiers

In bb-sign, "archived" refers to two different things:

- **An envelope moves to Archived.** <Fact of={ENVELOPE.archiveAfterDays} unit="days" /> after it was
  created, a closed envelope moves to the **Archived** view. It is a list change, not a storage change:
  the envelope becomes read-only, its documents and its evidence certificate still download normally
  and each signer's link still gives access to their copy. See
  [Archived envelopes](/en/sign/sending/archived-envelopes/).
- **A file moves to a tier that needs a restore.** If your organization's policy has a tier marked
  "Needs a restore, ready in hours", a signed PDF, or the original of a completed envelope, that reaches
  that tier is kept all the same, but it has to be restored before it can be downloaded. With the
  standard configuration no file reaches such a tier. Drafts, the evidence certificate and the audit
  trail are never moved.

## Request a restore from the envelope page

If a file needs a restore, the envelope's **Documents (N)** section shows, instead of its download
button, the **Request restore** button and the note "\{file\}: archived. Request its restore to download
it." The envelope can be in **Envelopes** or in **Archived**: either way, you open it from its title.

Press **Request restore**. While it is being restored, the file says it is restoring and, once it is
available, you receive an email with a link to the envelope. Then return to the envelope page: the
download button is back, with the date until which you can use it. The restored copy can be downloaded
for <Fact of={RESTORE.days} unit="days" />; after that it goes back to its storage
tier{RESTORE.requestableAgainAfterWindow.value && ' and can be requested again'}.

A restore can be requested by those who can download the envelope's documents: the auditors,
contributors and managers of its workspace and the organization's administrators. Without that
permission, the page does not offer the button.

### File states

| What you see next to the file | What it means | What to do |
|---|---|---|
| "\{file\}: archived. Request its restore to download it." | The file is in a tier that needs a restore. | Press **Request restore**. |
| "\{file\}: restoring. We will email you when it is available (usually within a few hours)." | Your request is in progress. | Wait for the email. You do not need to press the button again. |
| "\{file\}: being restored (usually within a few hours). If you did not request it, request it to be emailed when it is ready." | Someone else asked for the same file and the restore is in progress. | Press **Request restore** if you want the email: your request joins the one already running. |
| "\{file\}: restored, available until \{date\}." | The restored copy can be downloaded. | Download it before that date and store it in your systems. |
| "\{file\}: no longer available (<Fact of={ORG_STORAGE.defaultRetentionDays} />-day period ended)." | The file reached the end of its retention period and was deleted. The message names the standard configuration's period. | Use the copy your organization kept. |

### How long it takes

A restore usually takes a few hours, with no guaranteed time; from the deepest tier, up to about
<Fact of={ORG_STORAGE.deepestRestoreMaxHours} unit="hours" />. If several people ask for the same file,
bb-sign runs a single restore and emails each of them. If the restore has not finished within
<Fact of={RESTORE.timeoutHours} unit="hours" />, it is treated as failed and the email says so; you can
request it again.

### If the request is not accepted

| Message | What happened | What to do |
|---|---|---|
| "Your organization already has too many restores in progress. Try again when one finishes." | Your organization has the maximum of <Fact of={RESTORE.maxActivePerOrg} /> restores in progress. Users' and API credentials' restores count; signers' do not. | Wait for one to finish and press **Request restore** again. |
| "The archive storage is not responding right now. Try again in a few minutes." | The storage did not answer and the request was not recorded. | Try again in a few minutes. |
| "This file is no longer available: its <Fact of={ORG_STORAGE.defaultRetentionDays} />-day period has ended." | The file was deleted at the end of its period. | Use the copy your organization kept. |
| "Could not request the restore" | The request did not complete for another reason. | Reload the page and try again. If it repeats, send your administrator the reference shown in the notice. |

## Request a restore from an integration

An integration requests a file's restore through the API, with the same download permission. Say which
file it needs: `SIGNED` (the signed PDF) or `ORIGINAL` (the uploaded document).

```bash
curl -X POST "$API_BASE/api/v1/envelopes/$ENVELOPE_ID/documents/$DOCUMENT_ID/restore" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"kind": "SIGNED"}'
```

| Response | What it means | What to do |
|---|---|---|
| `202` | The restore started, or was already running and your request joined it (`alreadyInProgress: true`). | Wait for the `document.restored` webhook. |
| `200` | The file does not need a restore. | Download it now. |
| `410 DOCUMENT_DELETED` | The file reached the end of its retention period and no longer exists. | Use the copy your system archived. |
| `429 RESTORE_LIMIT_REACHED` | Your organization has too many restores in progress. | Request it again when one finishes. |
| `503 ARCHIVAL_STORAGE_UNAVAILABLE` | The storage did not answer and the request was not recorded. | Try again later. |

Each file's state is in the envelope's document list, in `original.availability` and
`signed.availability`:

```bash
curl "$API_BASE/api/v1/envelopes/$ENVELOPE_ID/documents" -H "Authorization: Bearer $TOKEN"
```

| Value | What it means |
|---|---|
| `AVAILABLE`, `RESTORED` | It can be downloaded. |
| `ARCHIVED` | It needs a restore. |
| `RESTORE_IN_PROGRESS` | It is being restored. |
| `DELETED` | It reached the end of its retention period. |

The error codes are in [Errors](/en/sign/developers/errors/).

## The signer's copy

Each signer can ask for their own signed copy from the link they signed with, even after the signing
period has ended. If their copy needs a restore, the page shows "Your signed copy is archived. Request
it and we will email it to you when it is available." and the **Request my copy** button. When they
press it, the page confirms "We will email you your copy when it is available, usually within a few
hours." and the signer receives the restore email, with a link to that same page, once the copy is
ready.

Each link allows <Fact of={RATE_LIMITS.signerRestorePerLink} /> requests and each connection
<Fact of={RATE_LIMITS.signerRestorePerIp} /> within <Fact of={RATE_LIMITS.signerRestoreWindowMinutes} unit="minutes" />.
What the signer sees in each case is described in [Sign and download](/en/sign/signing/sign-and-download/).

## The notice when the file is available

### The email

When a restore ends, each person who asked for it, in the application or as a signer, receives the
email `Tu solicitud de restauración de documentos / Your document restore request`, in Spanish and then
in English. For each file, the email says whether it is available and until when (in UTC), or why it
is not.{RESTORE.emailLinksToEnvelopeOrSigningPage.value && ' It does not carry the files: its link leads to the envelope page, or to the signing page if you asked as a signer, where they are downloaded.'}{RESTORE.emailGenericWithoutConfirmedAccess.value && ' If bb-sign cannot confirm that you can still download the envelope\'s documents, you receive a generic email, with no envelope title and no file names, only the link.'}

| What the email says | What to do |
|---|---|
| "No longer available: it was deleted after its <Fact of={ORG_STORAGE.defaultRetentionDays} unit="days" />." | Use the copy your organization kept. |
| "The restore took longer than expected; you can request it again." | Press **Request restore** or **Request my copy** again. |
| "It could not be restored." | Request it again. If it repeats, contact your administrator. |

### The webhook

API credentials are not emailed: an integration that requests a restore learns of it only from the
`document.restored` webhook. Subscribe to that event in **Settings**, **Webhooks** tab. The event names
the document, the file (`kind`), the outcome (`outcome`: `RESTORED`, `AVAILABLE` or `FAILED`, with its
`reason`) and until when it is available (`availableUntil`). It carries neither the file nor a download
link: it carries `downloadPath`, the envelope's document list, where you get a short-lived download
link. See [Webhooks](/en/sign/developers/webhooks/).

The evidence certificate never needs a restore: it downloads directly throughout its period.

## Keep every envelope in your systems

The safest way to meet the period is to copy every envelope to your organization's systems as soon as
it completes. An administrator can automate it:

1. Subscribe to the `envelope.completed` webhook, and to `envelope.evidence_issued` for a certificate
   that arrives later.
2. When it arrives, read `data.documentsPath` and call that path with your credential, which needs the
   document download permission: for each document it returns a short-lived download link for the
   signed PDF (`signedUrl`).
3. Download each signed PDF and compare its SHA-256 with the webhook's
   `data.documents[].signedSha256`. If they match, the file is exactly the one bb-sign sealed.
4. Download the evidence certificate from `data.evidenceCertificate.downloadPath`, which returns a link
   valid for <Fact of={EVIDENCE.downloadLinkSeconds} unit="seconds" />, and compare its SHA-256 with
   `data.evidenceCertificate.sha256`.
5. Also store `data.retention.deletesAt`: it is the date from which bb-sign will no longer have the
   files.

To compute the SHA-256 of a downloaded file (on Linux, `sha256sum` does the same):

```bash
shasum -a 256 documento-firmado.pdf
```

If the webhook says `signedDocumentsStatus: PREPARING`, the signed PDFs did not exist yet: do not
compare the hash, and request `data.documentsPath` again later.
