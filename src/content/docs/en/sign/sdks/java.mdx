The Java SDK connects your services to the bb-sign API: it manages tokens, retries safely and
verifies webhook signatures. The coordinates are
<code><Fact of={SDK.java.groupId} />:<Fact of={SDK.java.artifactId} />:<Fact of={SDK.java.version} /></code>.
This page merges the SDK's `README.md` and its `README-INSTALL.md`.

Requires **Java <Fact of={SDK.java.minJava} />** or newer.

## Installation

The SDK is delivered as four files: the jar, its pom, a `.sha256` and the installation guide. You
can also build it from source (see [Build from source](#build-from-source)). Install the jar into
your local Maven repository and declare it as a dependency.

<Steps>
1. Verify the integrity of the file you received, and that the `.sha256` is the one from the most
   recent handover (see [Versions](#versions)):

   ```bash
   shasum -a 256 -c bb-sign-sdk-java-0.1.0-SNAPSHOT.jar.sha256
   ```

2. Install it. **`-DpomFile` is required:**

   ```bash
   mvn install:install-file \
     -Dfile=bb-sign-sdk-java-0.1.0-SNAPSHOT.jar \
     -DpomFile=bb-sign-sdk-java-0.1.0-SNAPSHOT.pom
   ```

3. Declare it as a dependency:

   ```xml
   <dependency>
     <groupId>co.binarybridges.sign</groupId>
     <artifactId>bb-sign-sdk-java</artifactId>
     <version>0.1.0-SNAPSHOT</version>
   </dependency>
   ```
</Steps>

<Aside type="caution" title="Always include -DpomFile">
  Without this parameter, Maven generates a pom with no dependencies. The install and the build
  complete without errors, but the first API call fails at runtime with `NoClassDefFoundError` for
  a Retrofit or okhttp class. The pom is what declares okhttp, Retrofit and Jackson. If that error
  appears, reinstall with `-DpomFile`.
</Aside>

### Dependencies

**The build must have access to Maven Central.** The SDK is a plain jar, not a shaded one: your
build resolves okhttp, Retrofit and Jackson and aligns them with the versions you already use. This
avoids conflicts with Jackson, which is present in most Java services.

If your build has no access to Maven Central, contact us before you start the integration to
receive a shaded variant of the SDK.

## Quickstart

The complete example fits in one file. Credentials are created in bb-sign under **Settings**, tab
**API credentials**; the secret is shown once, at creation.

```java
import co.binarybridges.sign.sdk.BbSignClient;
import co.binarybridges.sign.sdk.generated.model.*;
import java.time.OffsetDateTime;
import java.util.List;

try (BbSignClient client = BbSignClient.builder()
        .baseUrl(System.getenv("BBSIGN_BASE_URL"))
        .tokenUrl(System.getenv("BBSIGN_TOKEN_URL"))
        .clientCredentials(System.getenv("BBSIGN_CLIENT_ID"), System.getenv("BBSIGN_CLIENT_SECRET"))
        .build()) {

    CreateEnvelopeRequest request = new CreateEnvelopeRequest()
            .title("Q3 Agreement")
            .otpRequired(false)
            .expiresAt(OffsetDateTime.now().plusHours(72))
            .signers(List.of(new CreateSignerSpec()
                    .email("signer@example.com")
                    .name("A Signer")
                    .signOrder(1)));

    EnvelopeResponse envelope = client.execute(client.envelopes().createEnvelope(request));
    System.out.println("Created " + envelope.getId());
}
```

Read the credentials from environment variables, outside your source code. The secret is stored
only in Keycloak and bb-sign keeps no copy; if it is lost, rotate it, which invalidates the old one
**immediately**.

### What the client covers

The client exposes `envelopes()`, `documents()` and `verification()`:

| Accessor | Operations |
|---|---|
| `envelopes()` | Create, list, read, attach documents, add signers, send, cancel, count by status, list the documents with their links, and `restoreEnvelopeDocument` (request a restore of an archived file) |
| `documents()` | `uploadDocument`. The generated methods send JSON, so a multipart upload uses okhttp (see the [walkthrough](/en/sign/developers/envelope-walkthrough/#2-upload-the-document)) |
| `verification()` | `verifyDocument` (the QR code seal) and `verifyDocumentFile`, which **does not work today**: see [Check a file](#check-a-file) |

**Not in the client:** the evidence certificate, `GET /api/v1/workspaces` and agreement copies.
Their interfaces are generated, but `BbSignClient` does not expose them. Call them over HTTP with a
token obtained as in the [walkthrough](/en/sign/developers/envelope-walkthrough/#1-get-a-token);
step 8 of that walkthrough downloads the evidence certificate in Java.

### List by page

```java
client.eachPage(
        page -> client.envelopes().listEnvelopes(page, 50, null, null, null, null, null, null),
        PagedEnvelopeResponse::getContent)
    .forEach(envelope -> System.out.println(envelope.getTitle()));
```

Pages are fetched on demand as you iterate, so going through thousands of envelopes does not load
them all into memory.

## Verify a webhook

`Webhooks.verify` checks the signature over the body exactly as received. Declare the body as
`byte[]` in your handler, and read the event with an `ObjectMapper` configured like the SDK's own:

```java
import co.binarybridges.sign.sdk.Webhooks;
import co.binarybridges.sign.sdk.generated.model.WebhookEvent;
import com.fasterxml.jackson.databind.DeserializationFeature;
import com.fasterxml.jackson.databind.ObjectMapper;
import com.fasterxml.jackson.datatype.jsr310.JavaTimeModule;

// ISO-8601 dates (JavaTimeModule), and new fields ignored instead of fatal.
private static final ObjectMapper MAPPER = new ObjectMapper()
        .registerModule(new JavaTimeModule())
        .disable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES);

@PostMapping("/webhooks/bb-sign")
public ResponseEntity<Void> receive(
        @RequestHeader("X-BBSign-Signature") String signature,
        @RequestBody byte[] rawBody) throws IOException {   // byte[], NOT a DTO

    if (!Webhooks.verify(signature, rawBody, System.getenv("BBSIGN_WEBHOOK_SECRET"))) {
        return ResponseEntity.status(401).build();
    }

    WebhookEvent event = MAPPER.readValue(rawBody, WebhookEvent.class);
    switch (event.getType()) {
        case ENVELOPE_COMPLETED -> onCompleted(event.getData());
        case SIGNER_SIGNED      -> onSigned(event.getData().getSigner());
        default                 -> { /* ignore other types, UNKNOWN_DEFAULT_OPEN_API included */ }
    }
    return ResponseEntity.ok().build();
}
```

`event.getType()` returns the `WebhookEvent.TypeEnum` enum, not a `String`, so the `case` labels use
its constants. An unconfigured `new ObjectMapper()` does not work: it cannot read the dates
(`OffsetDateTime`) and fails on any new field, and the contract adds fields without changing
version. <code>{SDK.java.jsr310Dependency.value}</code> is already a dependency of the SDK, at the
Jackson version <Fact of={SDK.java.jacksonVersion} /> its pom declares.

<Aside type="caution" title="Use the current SDK handover">
  An event type the SDK does not know reads as `UNKNOWN_DEFAULT_OPEN_API`. Earlier handovers of
  <code><Fact of={SDK.java.version} /></code>, with the same version number, throw an exception on a
  new type such as `envelope.evidence_issued` or `document.restored`. Check the `.sha256` against
  the one from the most recent handover.
</Aside>

### Capture the raw body

The signature covers **the exact bytes received**. If the parameter is declared as a DTO, Spring
parses the JSON and hands you an object; re-serializing it produces different bytes (key order and
whitespace change) and verification fails even though the object is correct.

- **Spring MVC**: `@RequestBody byte[]` or `@RequestBody String`, or a `ContentCachingRequestWrapper`
  if you also need the parsed form.
- **Jakarta Servlet**: read `request.getInputStream()` once, before any other component.

The SDK takes `byte[]` rather than `String` deliberately: the type guides you to the correct use.

### Respond immediately, process afterwards

Return 2xx as soon as the signature is valid and process the event asynchronously. bb-sign retries
on a schedule spanning roughly <Fact of={WEBHOOKS.retryLadderHoursApprox} unit="hours" />, and after
<Fact of={WEBHOOKS.disableAfterLadders} /> consecutive exhausted schedules it **disables the
endpoint**; asynchronous processing keeps the response fast under load.

### Deduplicate on the event id

`X-BBSign-Event-Id` is stable across retries and redeliveries of the same event. Delivery is
at-least-once, so an event can arrive twice; use the id as an idempotency key.

### Secret rotation

While a rotation window is open, the header carries two `v1=` values. `Webhooks.verify` accepts
either, which lets you deploy the new secret without downtime and with no extra configuration.

### Test the handler

Verification is time-sensitive: a signature older than
<Fact of={WEBHOOKS.toleranceSeconds} unit="s" /> is rejected, so a fixed fixture in a unit test
stops being valid. Use the clock-bearing overload:

```java
Webhooks.verify(signature, rawBody, secret, Duration.ofSeconds(300), Instant.ofEpochSecond(1760000000L));
```

## Check a file

`POST /api/v1/verify/file` takes a PDF's bytes (`application/octet-stream`, not multipart), computes
their SHA-256 on the server and answers whether it is a document bb-sign signed. It is public, does
not store the file and accepts up to <Fact of={VERIFY.fileMaxMb} unit="MB" />, limited to
<Fact of={RATE_LIMITS.verifyFilePerMinutePerClient} /> requests a minute per client.

{SDK.javaVerifyFileSendsPath.value && (
  <Aside type="caution" title="verifyDocumentFile sends the path, not the file">
    <code>client.verification().verifyDocumentFile(File)</code> serializes the <code>File</code> as
    JSON, so it sends the file's path in quotes instead of its bytes, and the answer never matches.
    This is a known SDK defect. Until it is fixed, make this call over HTTP:
  </Aside>
)}

```java
HttpRequest check = HttpRequest.newBuilder(URI.create(System.getenv("BBSIGN_BASE_URL") + "/api/v1/verify/file"))
        .header("Content-Type", "application/octet-stream")
        .POST(HttpRequest.BodyPublishers.ofFile(Path.of("contract-signed.pdf")))
        .build();
HttpResponse<String> response = HttpClient.newHttpClient().send(check, HttpResponse.BodyHandlers.ofString());
if (response.statusCode() == 429) {
    String retryAfter = response.headers().firstValue("Retry-After").orElseThrow();
    // RATE_LIMITED: wait retryAfter seconds, then check again
} else {
    VerifyFileResponse result = MAPPER.readValue(response.body(), VerifyFileResponse.class);
    System.out.println(result.getMatch() + " " + result.getSha256());
}
```

Only signed PDFs match: an unsigned original never does. `GET /api/v1/verify`, by contrast, checks
the seal printed in the QR code against bb-sign's records and does not read the PDF.

## Retries

`GET` requests are retried on 5xx errors and connect timeouts, with exponential backoff and full
jitter, from <Fact of={SDK.retryBaseMs} unit="ms" /> up to <Fact of={SDK.retryMaxBackoffMs} unit="ms" />.

**A `POST` whose response was not received is not retried.** If `createEnvelope` times out, the
outcome is unknown: the envelope may already exist, and a retry would create a second agreement
sent to the same people. The API does not use idempotency keys.

If a create times out, **list before you retry**:

```java
try {
    client.execute(client.envelopes().createEnvelope(request));
} catch (BbSignException e) {
    if (e.statusCode() == 0) {
        // Never reached bb-sign, or the answer was lost. Check before sending again.
    }
}
```

`429` and `503` are also retried for `POST`, because they indicate the server did not process the
request. The SDK **does not honour `Retry-After`**: on a `RATE_LIMITED`, its retries arrive before
the window opens and fail again. If you receive <code>{QUOTA.httpStatusWhenExhausted.value}</code>,
wait the `Retry-After` seconds before calling again; that wait is up to your code.

## Errors

Every non-2xx response throws `BbSignException`, which exposes `statusCode()`. `0` indicates the
request got no answer.

| Status | Meaning |
|---|---|
| 400 | Malformed request or failed validation |
| 401 | Credentials rejected. The SDK refreshes the token and retries once before surfacing this |
| 403 | Authenticated, but this credential lacks the organization permission |
| 404 | The resource does not exist, or belongs to another organization or a workspace the credential cannot see. Deliberately indistinguishable |
| 408 | The upload to verify by file took longer than the deadline |
| 409 | The resource is not in a state that allows the operation, e.g. sending an already-sent envelope or requesting the certificate of an envelope that is not completed |
| 410 | The file you asked to restore is past its retention period |
| 413 | The file sent to verify by file is above the size limit |
| 429 | The server did not process the request: an exhausted quota (`QUOTA_EXCEEDED`), a rate limit (`RATE_LIMITED`) or too many restores in progress (`RESTORE_LIMIT_REACHED`) |
| 503 | A service the operation depends on did not answer |

{SDK.errorCarriesStatusOnly.value && (
  <p>
    <code>BbSignException</code> carries the status only, not the body or its <code>code</code>: a
    quota 429 and a rate-limit 429 look the same. If you need the <code>code</code>, make that call over
    HTTP and read the body.
  </p>
)}

Exception messages never include your secret or access token, even when bb-sign's response
contains them. [Errors](/en/sign/developers/errors/) includes the full table and the error body.

## What is new in the contract

The SDK is generated from the OpenAPI contract, so a current handover already types the fields
added since the first one:

- `EnvelopeResponse`: `archived`, `archivedAt`, `retention` and `restoresInProgress`.
- `DocumentWithUrlsResponse`: `originalSha256`, plus `original` and `signed` (`DocumentFile`, with
  `availability`, `deletesAt`, `archivesAt`, `availableUntil` and `restorable`).
- `WebhookEventData`: `evidenceStatus`, `signedDocumentsStatus`, `documents`, `documentsPath`,
  `evidenceCertificate`, `auditChainHead`, `retention` and `document`; `WebhookEventSigner.authMethod`.
- The `ENVELOPE_EVIDENCE_ISSUED` and `DOCUMENT_RESTORED` event types.

The SDK's `CHANGELOG.md` lists every change, including the ones that need a source change on your
side.

## Versions

The version is <code><Fact of={SDK.java.version} /></code>. Later handovers kept that number even
though they added operations and fields, so the version alone does not tell you which jar you have.
Compare your jar's `.sha256` with the one from the most recent handover we sent you.

## Security guarantees

- **Credentials stay out of logs.** The SDK includes no logging interceptor and no hook to install
  one. Avoid adding okhttp's `HttpLoggingInterceptor` at `BODY` yourself: it prints the
  `Authorization` header and the token form body verbatim.
- **TLS is always verified.** Certificate verification cannot be disabled.
- **No duplicate writes.** A write with an unknown outcome is not retried (see
  [Retries](#retries)).

## Build from source

```bash
cd sdk-java
mvn verify          # regenerates the client, compiles, runs the tests
./verify.sh         # the CI gate: drift, Jackson-not-Gson, plugin survival
mvn package         # writes the handover artifact to target/handover/
```

The client under `src/main/java/co/binarybridges/sign/sdk/generated/` is **generated and
committed** code: regenerate it rather than editing it. It is committed so that every spec change
shows up as a reviewable diff.
