**Who:** organization admin (platform admins too, from each organization's page). **Where:** Settings,
"API credentials" tab (`/settings`).

"A credential lets a system call the bb-sign API on your organization's behalf. It is scoped to this
organization and cannot see anyone else's envelopes". A credential is a "Client ID" and "Client
secret" pair with which the system obtains access tokens.

## Create a credential

<Steps>

1. Press "New credential".

2. Enter the "Label": "What will use this credential — for example "Billing system" or "Nightly
   export"".

3. Under "Access", choose the "Workspace" and the "Role" (Viewer, Auditor or Manager). "The
   integration gets this role in this workspace. General with Manager is the default".

4. Press "New credential". "Save this secret now" opens with the "Client ID" and the "Client
   secret". Copy them into your secret manager before closing.

</Steps>

<Aside type="caution" title="The secret is shown once">
  The dialog says so: "This is the only time the secret will be shown". Its text adds that it "is
  stored hashed"; in fact bb-sign keeps no copy of the secret, hashed or otherwise. It lives only in
  the identity server (Keycloak), from which it cannot be recovered either. If you lose it, the only
  way out is to rotate the credential.
</Aside>

## What a credential can do

A credential acts with the role you gave it in each workspace, like a person: as Manager in General
it creates, sends and cancels envelopes and downloads documents of that workspace; as Viewer it
only sees them. To give it access to more workspaces, add it as a member from
[Workspaces and members](/en/sign/admin/workspaces-and-members/); the credential's row lists the
"Workspaces this key can act in".

A credential never administers: it cannot create credentials or webhooks, nor create workspaces or
add members, even if the admin wants it to. The reason is in the
[Permissions matrix](/en/sign/admin/permissions/).

Your organization can hold up to <Fact of={AUTH.maxCredentialsPerOrg} /> active credentials.

## Rotate

"Rotate" generates a new secret for the same "Client ID". The "Rotate "label"?" dialog warns: "The
current secret stops working immediately. Any integration using it will fail until you redeploy it
with the new secret. There is no grace period". Confirm with "Rotate secret" and save the new secret
from the dialog. Plan the rotation with whoever deploys the integration.

## Revoke

"Revoke" ends the credential for good. The "Revoke "label"?" dialog says what really happens: "New
requests using this credential will be refused immediately. Requests using a token it already
obtained may keep succeeding" until that token expires. A token lives
<Fact of={AUTH.tokenLifetimeSeconds} unit="s" />; that is the maximum.

Meanwhile the row shows "Revoked — draining" and "Tokens this credential already issued stop working
at time". Then it becomes "Revoked" and stays listed for
<Fact of={AUTH.revokedCredentialListedDays} unit="days" />, so you can check what was revoked.
Creation and revocation are recorded in the [audit trail](/en/sign/admin/audit-trail/).

## Statuses

| Status | Meaning |
| --- | --- |
| "Active" | Issues tokens and acts in its workspaces. |
| "Revoked — draining" | Issues no more tokens; the ones it obtained keep working until the time shown. |
| "Revoked" | No access. Leaves the list after the listing period. |

## If something goes wrong

| Message | What happened and what to do |
| --- | --- |
| ""label" was created but could not be given its access, so it was revoked. Nothing can use it." | The workspace access could not be set up. The revoked row is harmless; create the credential again in a moment. |
| "Could not create the credential." | The maximum number of active credentials was reached, or a temporary failure. Revoke one you do not use or try again later. |
