With your own certificate, every document signed in bb-sign is sealed in your organization's name,
and validators such as Adobe Acrobat recognize that seal. Whoever receives the PDF sees who sealed it
and can confirm it has not changed since it was signed. The PDF's signature box can also show your
organization's name and reason, which Binary Bridges configures in **Signature Appearance**.

The certificate seals the documents; it is not the digital signature of the people who sign. They
sign with bb-sign's electronic signature mechanism.

<Aside type="tip" title="Configure it before sending documents to third parties">
  Until your organization has its own certificate, bb-sign seals documents with the Binary Bridges
  testing certificate, <code><Fact of={CERTIFICATE.defaultSubject} /></code>. Validators show it as
  untrusted, because it is meant for trying the service. Sending envelopes is not blocked meanwhile.
</Aside>

## Which certificate to buy

Before paying, confirm with the issuer that the certificate meets these points:

- It is **in the organization's name**, as a legal-entity, public-function or document-signing
  certificate. The product's commercial name varies by issuer.
- It is delivered as a **PKCS#12 file (.p12 or .pfx) with an exportable private key**. bb-sign needs
  the file, so a certificate delivered on a USB token or that exists only in the vendor's cloud does
  not work for this use.
- It uses an **RSA key of at least <Fact of={CERTIFICATE.minKeyBits} unit="bits" />**. Only RSA
  keys are supported: bb-sign refuses elliptic-curve (EC), EdDSA and RSA-PSS keys.
- It has the key usage **digital signature** (`digitalSignature`) and, preferably,
  **non-repudiation** (`nonRepudiation`).
- It includes the **full certification chain**: the organization's certificate, the intermediates
  and the root.

## Where to buy it in Colombia

Buy from a **Digital Certification Entity (ECD) accredited by ONAC**. Confirm the current
accreditation in ONAC's directory ([onac.org.co](https://onac.org.co/)) before buying.

## Where to buy it in other countries

If your organization is outside Colombia, buy from a member of the **Adobe Approved Trust List
(AATL)**, so Adobe Acrobat trusts the seal without installing anything else. DigiCert, GlobalSign,
Sectigo, Entrust and SSL.com issue document-signing certificates in an organization's name.

Several of these products ship by default on a USB token or in a cloud HSM. Ask explicitly for a
**software certificate with an exportable key**.

List verified on 2026-10-07. Confirm with the entity that it delivers the certificate as a PKCS#12
file with an exportable key.

## Export the certificate with the full chain

The file must contain the organization's certificate, the intermediate certificates and the root.

- On Windows: open `certmgr.msc`, select the certificate and choose Export. Say you want to export
  the private key, choose the PKCS#12 format and tick "Include all certificates in the certification
  path if possible".
- With OpenSSL:

```bash
openssl pkcs12 -export -inkey clave.key -in certificado.crt -certfile cadena.pem -out organizacion.p12
```

If bb-sign cannot upload the file and the password is correct, export it again with OpenSSL 3's
`-legacy` option.

## Check the file before uploading

```bash
openssl pkcs12 -in organizacion.p12 -nokeys -info
```

The output must list the organization's certificate, the intermediates and the root.

To review a sealed PDF, open it in Adobe Acrobat and check the signature panel. The seal carries the
full chain you uploaded: the organization's certificate, the intermediates and the root. For Acrobat
to show the identity as valid, it must trust that root; if it does not recognize it, import it into
Acrobat as trusted.

## Upload the certificate

<Steps>

1. Open **Settings** and choose the **Certificate** tab. While your organization uses the testing
   certificate, you see the **Default testing certificate** notice, with the links **How to configure
   your certificate** and **Terms of service (Spanish)**.
2. Type a **Label** (for example, "Acme Corp 2026"), choose the **Certificate file (.p12, .pfx,
   .pem)** and type the **Password (if protected)**.
3. Press **Upload Certificate**.

</Steps>

When it finishes, the tab shows the label, the **Subject**, the **Issuer**, the expiry date after
**Expires:**, the start of the SHA-256 fingerprint and the chain status. When fewer than
<Fact of={CERTIFICATE.expiryHighlightDays} unit="days" /> remain before expiry, the date is highlighted
with a warning icon and shows the days left; an expired certificate shows **Expired:** in red.
To withdraw the certificate, use the **Remove certificate** button; from then on documents are sealed
with the testing certificate again.

The Binary Bridges platform administrator can also upload your organization's certificate, from the
**Signing Certificate** section of the organization's page.

## Chain status

When it receives the file, bb-sign checks the certification chain and shows its status:

| Status | What it means | What to do |
|---|---|---|
| **Complete chain** | The file includes every certificate up to the root. | Nothing. |
| **No root** | The chain stops before the root certificate. Validators that already trust the root accept the seal. | If your recipients do not trust that root, export again with the full chain. |
| **Leaf only** | The file does not include the certificates that issued yours. | Export again with the full certification path and upload it once more. |
| **Self-signed** | The certificate signed itself; no third party will trust it. | Buy a certificate from an accredited entity. |
| **Not checked** | Uploaded before chain checks existed. | Upload it again to check its chain. |

If the chain has a problem that does not prevent sealing, the certificate is uploaded and the tab
shows "The certificate was uploaded, with warnings" with the details. One of those warnings says the
file includes certificates that did not issue yours: export again with the certification path of
**this** certificate only. It is different from **Leaf only**, and each case has its own fix.

## Rules when the file is received

If "Failed to upload certificate" appears, check the file with the verification command and confirm
the password. bb-sign applies these rules:

| Rule | What bb-sign does |
|---|---|
| Accepted extensions | {CERTIFICATE.allowedExtensions.value.map((ext) => `.${ext}`).join(', ')} |
| Maximum file size | <Fact of={CERTIFICATE.maxFileMb} unit="MB" /> |
| Key type | RSA only. EC, EdDSA and RSA-PSS are rejected. |
| Key under <Fact of={CERTIFICATE.minKeyBits} unit="bits" /> | Rejected. |
| Key usage | Requires <code><Fact of={CERTIFICATE.requiredKeyUsage} /></code>. |
| Validity | The file is rejected if any certificate in the chain has expired or is not yet valid. |
| Chain | A broken or misordered chain, an issuer that is not a certification authority and a chain of more than <Fact of={CERTIFICATE.maxChainLength} /> certificates are rejected. |
| Private key | The file is rejected if the key does not match the certificate, is missing or there is more than one. |
| New upload | Replaces the previous certificate only when the new file passes every rule. If it is rejected, the current certificate keeps sealing. |
| Password | Stored encrypted and used only to seal. |
| PEM files | Accepted on upload, but sealing requires a PKCS#12. Upload a .p12 or .pfx file. |

Keep the `.p12` file and its password in your organization's secret manager and upload them only from
the application, never by email.

## Renew the certificate

Upload the renewed certificate before the current one expires. New seals use the renewed certificate
within <Fact of={CERTIFICATE.cacheMinutes} unit="minutes" />.

bb-sign emails every organization admin {CERTIFICATE.expiryNoticeDays.value.join(' and ')} days
before the organization's own certificate expires, with the expiry date and a link to **Settings**,
**Certificate** tab. The subject is "{expiryEmail?.subject}", with the number of days. The testing
certificate does not trigger these notices.

<Aside type="note" title="The notices are an aid">
  Clause 2.4 of the [Terms and conditions](/en/sign/legal/terms/) says so: "These notices are an aid;
  they do not transfer responsibility for the renewal to Binary Bridges."
</Aside>

Seals made since bb-sign <Fact of={VERIFY.qrUsesStoredFingerprintSince} /> store the fingerprint of
the certificate that sealed them, so they keep showing as valid in QR-code verification after a
certificate change. Older seals are compared with the **active** certificate: after a change they no
longer show as valid in that check, although the PDF stays intact and its signature panel in Acrobat
remains valid. See [Verify a signed document](/en/sign/signing/verify-a-document/).

Uploading and removing the certificate, and each expiry notice, are recorded in the organization's
[audit trail](/en/sign/admin/audit-trail/) with who did it.
