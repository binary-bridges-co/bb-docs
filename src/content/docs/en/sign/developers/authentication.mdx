Your integrations authenticate to bb-sign with an API credential and operate under the same
isolation guarantees as a member of the organization. An admin creates the credential in
**Settings**, tab **API credentials**; the **workspace roles** assigned to it determine what it can
do. This page is normative.

## A single identity model

A machine authenticates with OAuth2 **client credentials** against the `bbsign` realm. bb-sign
processes its token with the same code that processes a person's token, because Keycloak issues
both the same way:

- A Keycloak **service account is a real user record**, not a user-less principal.
- The **same attribute mapper** that adds the `bb_sign_org_id` claim to a person's token adds it to
  the machine token, from an attribute on the service-account user.
- Every org-scoping decision goes through a single point in the API, which reads that claim
  regardless of the grant type.

As a result, **org isolation is inherited**: a machine token is scoped by the same check as a
person's.

## Obtain a token

```bash
curl -s -X POST https://auth.binarybridges.co/realms/bbsign/protocol/openid-connect/token \
  -d grant_type=client_credentials \
  -d client_id=<your-client-id> \
  -d client_secret=<your-secret>
```

```json
{ "access_token": "eyJ...", "expires_in": 300, "token_type": "Bearer" }
```

Only `client_credentials` is accepted. The password grant is disabled on every client in the realm,
so a script cannot get a token with a person's email and password (Keycloak answers
`unauthorized_client`). An integration always uses its own credential, never a user's account.

Send it as a bearer token on every request:

```bash
curl -H "Authorization: Bearer $TOKEN" https://sign-api.binarybridges.co/api/v1/envelopes
```

### Required claims

| Claim | Value | Purpose |
|---|---|---|
| `bb_sign_org_id` | The owning org's UUID | Every org-scoped read and write resolves from this value. **If it is missing, the API returns 403** (see [Error statuses](#error-statuses)) |
| `realm_access.roles` | contains `org_api` | The role the organization-scoped endpoints admit |
| `aud` | contains `bb-sign` | If absent, the audience validator rejects the token before authorization is evaluated |
| `iss` | <Fact of={AUTH.expectedIssuer} /> | The API accepts tokens from this issuer only. A token from another realm or another host returns `401` |

Without the audience mapper, the token fails validation; without the org attribute, it fails
authorization. In both cases access is denied. Credentials created from **Settings** carry all of
these claims.

<Aside type="note" title="Token lifetime">
  A token is valid for <Fact of={AUTH.tokenLifetimeSeconds} unit="s" /> (`expires_in`). It is
  validated against the realm's JWKS with **no introspection call**, so it stays valid until it
  expires even if the credential has been revoked. Any revocation of access takes effect within
  that window.
</Aside>

## Credential scope

At organization level a credential holds only these permissions:

<ul>
  {orgApiPermissions.map((key) => (
    <li><code>{key}</code></li>
  ))}
</ul>

With them it lists the label keys and the workspaces it belongs to, and reads agreement copies (see
[Agreement copies](#agreement-copies)). What it can do **with envelopes** depends on the role
it holds in each workspace. When the credential is created, the form asks for a workspace and a
role: "General with Manager is the default." An admin can later add it to other workspaces from
**Settings**, tab **Workspaces**, section **Members**.

<RolesMatrix locale="en" show="workspace" />

- `GET /api/v1/workspaces` returns General and the workspaces the credential holds a role in. Send
  one's `id` as `workspaceId` when creating an envelope; if you omit it, the envelope goes to
  General.
- A credential can belong to at most <Fact of={AUTH.maxWorkspaceMembershipsPerPrincipal} /> workspaces.
- A role change applies when the credential's next token is issued, so within
  <Fact of={AUTH.tokenLifetimeSeconds} unit="s" />.
- The org is **always taken from the token**, never from the request. A machine does not send an
  `orgId` when creating an envelope; if it does, the envelope's organization does not change.

## Permissions reserved for people

A credential never receives these organization permissions, even if an admin tries to grant them.
They are escalation guards in the permission catalog:

<ul>
  {ORG_API_NEVER.map((key) => (
    <li><code>{key}</code></li>
  ))}
</ul>

Organizations, users, quotas, certificates, labels, credentials, webhooks and workspaces are
managed in the UI by an org admin, and so is the organization-wide audit trail. The signing
ceremony (`/api/v1/sign/**`) is public by design and scoped to one signer by the token in its link;
integrations do not use it.

The two kinds of denial are deliberately distinct:

| Request | Response |
|---|---|
| An operation the credential lacks the organization permission for | `403`, no body |
| An envelope or workspace the credential cannot see, or one that does not exist | `404`, identical to "does not exist" |

## Archived envelopes and one envelope's audit trail

About <Fact of={ENVELOPE.archiveAfterDays} unit="days" /> after it was created, a finished envelope
moves to **Archived**. It is not deleted: the envelope, its signers, its documents and its audit
trail stay readable through the same routes as an active envelope, by a credential too.

| Route | What the credential gets for an archived envelope | Permission in the envelope's workspace |
|---|---|---|
| `GET /api/v1/envelopes/{id}` | The envelope, with `archived: true` and `archivedAt` | `envelope:read` and `archive:read` |
| `GET /api/v1/envelopes/{id}/documents` | The documents, with download links | `document:download` and `archive:read` |
| `GET /api/v1/envelopes/{id}/evidence-certificate` and `/download` | The [evidence certificate](/en/sign/concepts/evidence-certificate/) | <code>{EVIDENCE.downloadPermission.value}</code> and `archive:read` |
| `GET /api/v1/audit/envelopes/{id}/events` | The envelope's audit trail | `audit:read` and `archive:read` |

Every workspace role from *viewer* up holds `archive:read`. Without it, or for another
organization's envelope, the answer is `404`, the same as a missing id. An archived envelope is
read-only: send, cancel, add-signer, upload and label changes on its id return `404`.

One envelope's audit trail (active or archived) is read with `audit:read`, which the
<code>{AUDIT.envelopeTrailReaders.value.join(', ')}</code> roles hold:

| Route | Response |
|---|---|
| `GET /api/v1/audit/envelopes/{id}/events` | The envelope's events |
| `GET /api/v1/audit/envelopes/{id}/verification` | Whether the hash chain verifies: <code>{AUDIT.verificationStatuses.value.join(', ')}</code> |
| `GET /api/v1/audit/envelopes/{id}/export` | The trail in the <code>{AUDIT.exportFormat.value}</code> format, as a download |

`/verification` and `/export` share a limit of <Fact of={AUDIT.readRatePerMinute} /> calls a minute
per credential; above it they return `429 RATE_LIMITED` with `Retry-After`.
{!RATE_LIMITS.auditReadThrottledRoutes.value.includes('events') && <> <code>/events</code> has no such limit.</>} An export of more than
<Fact of={AUDIT.exportMaxRows} /> rows returns `413 AUDIT_EXPORT_TOO_LARGE`: request it in pages with
`fromSeq` and `limit` (at most <Fact of={AUDIT.exportPageMaxRows} /> rows a page). Every export is
recorded in the envelope's own trail, with the credential as the actor. These routes are not yet in
the published OpenAPI contract or the [API reference](/sign/api/). The organization-wide trail
(`/api/v1/audit/org-events`) and the rest of `/api/v1/audit/**` remain reserved for people.

## Agreement copies

With `agreement:read`, a credential reads an agreement copy with
`GET /api/v1/agreement-copies/{copyId}`: the exact, immutable text, with its version, its language
and its `contentSha256`. Another organization's copy returns `404`.
{!AGREEMENTS.pinAtSendInProduction.value && ' In production, copies are not yet pinned to envelopes when they are sent, so no envelope cites a copy.'}

## Error statuses

| Status | Meaning | Usual cause | Action |
|---|---|---|---|
| `401` | No token, expired token, or a token the realm will not validate | Missing `Authorization` header; token older than <Fact of={AUTH.tokenLifetimeSeconds} unit="s" />; token issued by another realm or host (its `iss` is not <Fact of={AUTH.expectedIssuer} />) | Request a new token from the production token URL; check the `Bearer ` prefix |
| `403` on a workflow endpoint | Authenticated, but not permitted at organization level | Calling a management operation that exists only in the UI | Confirm the operation exists in the [API reference](/sign/api/) |
| `403` on `GET /api/v1/envelopes` specifically | The token carries `org_api` but **not `bb_sign_org_id`** | A credential not created from **Settings** | Revoke it and create a new one in **Settings**, tab **API credentials** |
| `404` on an envelope or workspace | The credential holds no role in that workspace, or the id is wrong | A workspace never assigned to the credential | Ask an admin to add the credential under **Members**, or use General |
| `429 RATE_LIMITED` on `/api/v1/audit/**` | The credential's audit read limit was exceeded | Repeated exports or verifications within one minute | Wait the `Retry-After` seconds before calling again |

In the case of the third row, access is denied: a token without the org claim receives no
organization's data.

## Token lifetime and revocation

- A token is valid for <Fact of={AUTH.tokenLifetimeSeconds} unit="s" /> and is not validated by
  introspection.
- **Revoke** stops new tokens immediately. The confirmation states that requests using a token
  already obtained may keep succeeding until that token expires: "revoking does not cut access
  that is already in flight." The credential is listed as **Revoked — draining** until the last
  token it issued expires, then as **Revoked**, and stays listed for
  <Fact of={AUTH.revokedCredentialListedDays} unit="days" />. When responding to a leak, treat the
  credential as active until that time has passed.
- **Rotate** replaces the secret with no grace period: "The current secret stops working
  immediately. Any integration using it will fail until you redeploy it with the new secret."
- An organization can hold at most <Fact of={AUTH.maxCredentialsPerOrg} /> active credentials.

## Create a credential

An org admin creates credentials from the UI:

<Steps>
1. Open **Settings**, tab **API credentials**, and select **New credential**.
2. Give it a label that identifies the system that will use it and, under **Access**, choose the
   workspace and the role.
3. Copy the **Client ID** and the **Client secret**. The secret is shown once: it is stored only in
   Keycloak and bb-sign keeps no copy.
4. Deliver both values to the system that will use them through its secret store, never through
   source control or chat.
</Steps>

Management from the UI is described in [API credentials](/en/sign/admin/api-credentials/).
