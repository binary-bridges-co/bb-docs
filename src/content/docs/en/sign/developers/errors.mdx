The API returns a small set of statuses and each has a single meaning, so your integration can
decide what to do from the code alone. This page describes each status, the body that comes with
it and why an envelope the credential cannot access returns `404`.

## Status codes

| Status | Meaning | Action |
|---|---|---|
| `400` | Malformed request or failed validation (`code` `VALIDATION_FAILED`). On signing, also an image or a `signatureMethod` the server does not accept (`code` says which) | Compare the body with the schema in the [API reference](/sign/api/); dates must be ISO-8601 |
| `401` | Credentials rejected: no token, an expired token (a token is valid for <Fact of={AUTH.tokenLifetimeSeconds} unit="s" />), a token from another issuer or a token the realm will not validate | Request a new token and check the `Bearer ` prefix. Both SDKs refresh the token and retry once before reporting this status |
| `403` | Authenticated, but the credential lacks the organization permission | The operation is a management operation that exists only in the UI, or the token has no `bb_sign_org_id`. See [Machine authentication](/en/sign/developers/authentication/) |
| `404` | The resource does not exist, or belongs to another organization or a workspace the credential cannot see. Deliberately indistinguishable | Check the id; if the workspace is the issue, ask an admin to grant the credential a role there |
| `408` | The upload to verify by file took longer than the deadline (<Fact of={VERIFY.fileMaxSeconds} unit="s" />), or the signing body arrived too slowly (at most <Fact of={SIGN_REQUEST.maxSeconds} unit="s" />). A client that stops sending entirely may get a `408` with no body, or an empty `401` | Try again |
| `409` | The resource is not in a state that allows the operation, for example sending an already-sent envelope, requesting the certificate of an envelope that is not completed, signing documents that changed, or signing when the code was verified more than <Fact of={OTP.verifiedValidityMinutes} unit="min" /> ago | Read the resource first and act on its state; `code` names the case (next table) |
| `410` | The file you asked to restore is past its retention period | None: use the copy your system archived |
| `413` | The body is too large: a file above <Fact of={VERIFY.fileMaxMb} unit="MB" /> on verify by file, an audit export above <Fact of={AUDIT.exportMaxRows} /> rows, or a signature above <Fact of={SIGN_REQUEST.maxBodyMib} unit="MiB" /> | Send the right file, request the export in pages, or make the signature image smaller |
| `422` | A business rule rejected the request, for example sending an envelope with no document or no signer | Fix the envelope and try again |
| <code>{QUOTA.httpStatusWhenExhausted.value}</code> | The server did not process the request. `code` says why: an exhausted quota (`QUOTA_EXCEEDED`), a rate limit (`RATE_LIMITED`) or too many restores in progress (`RESTORE_LIMIT_REACHED`) | Depends on `code`: raise the quota, wait for `Retry-After`, or wait for the restores to end |
| `503` | A service the operation depends on did not answer. On signing, `SIGNING_BUSY`: bb-sign is at its signing capacity right now | Try again later; for `SIGNING_BUSY`, after the seconds in `Retry-After` |
| `0` (SDKs only) | The request got no answer: it never reached bb-sign or the reply was lost | For a `POST`, **list before you retry** (see below) |

`401` and `403` are produced by the security filter chain and carry **no body**. Every other error
carries an `ErrorResponse`.

## Quota or rate limit

A <code>{QUOTA.httpStatusWhenExhausted.value}</code> is not always a quota. Read `code` before you
decide:

- **`QUOTA_EXCEEDED`**: the organization has exhausted a quota (the body carries `quota`). Retrying
  does not help until the platform administrator raises or renews it.
- **`RATE_LIMITED`**: the call exceeded a rate limit, and the response carries `Retry-After` with the
  seconds to wait. There are limits on verify by file
  (<Fact of={RATE_LIMITS.verifyFilePerMinutePerClient} /> a minute per client) and on the audit
  trail verification and export (<Fact of={RATE_LIMITS.auditReadPerMinutePerCaller} /> a minute per
  credential). Signing (`POST /api/v1/sign/{token}/sign`) has three:
  <Fact of={RATE_LIMITS.signPerMinutePerClient} /> signing requests a minute per client,
  <Fact of={RATE_LIMITS.signInFlightPerClient} /> uploads at once per client and
  <Fact of={RATE_LIMITS.signImageAttemptsPerLink} /> refused or in-review image attempts per link every
  <Fact of={RATE_LIMITS.signImageAttemptsWindowMinutes} unit="min" />. Outside the calls named here,
  the API applies no rate limit.
- **`RESTORE_LIMIT_REACHED`**: the organization has <Fact of={RESTORE.maxActivePerOrg} /> restores in
  progress. Wait for one to end.

A `503 SIGNING_BUSY` on signing is not a rate limit: bb-sign is at its signing capacity at that moment,
and `Retry-After` says <Fact of={SIGN_REQUEST.busyRetryAfterSeconds} unit="s" />. On a `429 RATE_LIMITED`
from signing, `Retry-After` depends on the limit reached: it is short when too many uploads were in
progress at once, and runs to the end of the window when the requests for the minute or the image
attempts for the link are used up. Always wait what it says.

The OpenAPI contract, and so the [API reference](/sign/api/), describes every
<code>{QUOTA.httpStatusWhenExhausted.value}</code> as an exhausted quota, including on the
rate-limited routes: what tells the cases apart is `code`.

## Error body

```json
{
  "status": 404,
  "error": "Not Found",
  "code": "WORKSPACE_NOT_FOUND",
  "message": "Workspace not found",
  "path": "/api/v1/envelopes",
  "timestamp": "2026-10-10T14:22:31Z",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736"
}
```

| Field | Type | Always present | Meaning |
|---|---|---|---|
| `status` | integer | yes | The HTTP status |
| `error` | string | yes | The HTTP reason phrase |
| `code` | string | yes | A stable machine-readable code, such as `WORKSPACE_NOT_FOUND` or `NOT_FOUND`. Base your logic on this field, not on `message` |
| `message` | string | yes | Human-readable text; its wording may change |
| `path` | string | yes | The request path |
| `timestamp` | date-time | yes | When the error was produced |
| `traceId` | string | no | Include it when you contact support; it locates the request in our logs |
| `quota` | `QuotaViolation` | no | Only on <code>{QUOTA.httpStatusWhenExhausted.value}</code> |

### `QuotaViolation`

```json
{
  "status": 429,
  "error": "Too Many Requests",
  "code": "QUOTA_EXCEEDED",
  "message": "Organization quota exhausted",
  "path": "/api/v1/envelopes",
  "timestamp": "2026-10-10T14:22:31Z",
  "quota": { "dimension": "envelopes", "current": 500, "limit": 500 }
}
```

| Field | Type | Meaning |
|---|---|---|
| `dimension` | string | The affected quota: number of envelopes or storage used |
| `current` | integer | The organization's usage when the request was refused |
| `limit` | integer | The quota's limit |

The platform administrator sets quotas and org admins view them in the UI; see
[Quotas](/en/sign/concepts/quotas/).

## 404 instead of 403

<Aside type="note" title="Isolation between organizations">
  An envelope or workspace that belongs to another organization, or sits in a workspace where the
  credential holds no role, returns `404`, the same as an id that was never issued. This way, one
  organization cannot confirm that another's resources exist. Within your own organization, a
  workspace the credential cannot create in returns `404 WORKSPACE_NOT_FOUND`, and envelopes in
  workspaces it cannot read do not appear in lists.
</Aside>

`403` is reserved for organization-level denials: the token lacks a permission the operation
requires, or does not carry the org claim.

## Errors in the SDKs

Both SDKs turn every non-2xx response into a single exception type that carries the status and
nothing else: neither the `Response` object nor the headers. Logging the error therefore does not
expose your `Authorization` header. Messages never include your secret or access token, even when
bb-sign's response contains them.

| | JavaScript | Java |
|---|---|---|
| Type | `BbSignError` | `BbSignException` |
| Status | `error.statusCode` | `e.statusCode()` |
| No answer | `statusCode === 0` | `statusCode() == 0` |

```js
try {
  await client.envelopes.createEnvelope({ createEnvelopeRequest: request })
} catch (error) {
  if (error.statusCode === 0) {
    // Never reached bb-sign, or the answer was lost. List before you send again.
  }
}
```

```java
try {
    client.execute(client.envelopes().createEnvelope(request));
} catch (BbSignException e) {
    if (e.statusCode() == 0) {
        // Never reached bb-sign, or the answer was lost. List before you send again.
    }
}
```

Neither SDK retries a `POST` whose response was not received: the envelope may already exist, and
these are agreements sent to real people. `GET` requests are retried on 5xx errors and transport
failures; <code>{QUOTA.httpStatusWhenExhausted.value}</code> and `503` are retried for every
method, because they indicate the server did not process the request. The
[walkthrough](/en/sign/developers/envelope-walkthrough/) shows how to list before retrying.

The SDKs wait between retries with their own exponential backoff, from
<Fact of={SDK.retryBaseMs} unit="ms" /> up to <Fact of={SDK.retryMaxBackoffMs} unit="ms" />, and
**do not honour `Retry-After`**. On a `RATE_LIMITED`, the retries arrive before the window opens and
fail again; a `QUOTA_EXCEEDED` does not change on retry either. If your integration receives
<code>{QUOTA.httpStatusWhenExhausted.value}</code> repeatedly, wait before calling again.
