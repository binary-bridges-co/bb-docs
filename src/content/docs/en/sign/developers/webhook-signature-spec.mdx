**Status: NORMATIVE.** This document is the single source of truth for the bb-sign webhook
signature scheme. The dispatcher, the Java SDK and the JavaScript SDK implement it and refer to
this page. Part 1 defines how a delivery is signed; Part 2 defines its contents.

## 1. Headers

| Header | Value | Notes |
|---|---|---|
| `X-BBSign-Signature` | `t=<unix-seconds>,v1=<hex>` | See section 2 for grammar |
| `X-BBSign-Event-Id` | UUID v4 | **Stable across every redelivery of the same event.** The receiver's dedup key |
| `X-BBSign-Event-Type` | e.g. `envelope.completed` | Informational; the payload takes precedence over this header |

## 2. Signature header grammar

```text
signature-header = element *( "," element )
element          = scheme "=" value
scheme           = "t" / "v1" / <future scheme>
```

- Elements are comma-separated with **no whitespace**. Receivers **must** tolerate whitespace
  regardless.
- `t` appears exactly once: Unix **seconds**, base-10, no fractional part.

<Aside type="caution" title="t is the send time of the attempt, not the event time">
  The retry schedule runs for roughly <Fact of={WEBHOOKS.retryLadderHoursApprox} unit="hours" />,
  while the tolerance window is <Fact of={WEBHOOKS.toleranceSeconds} unit="s" /> (section 4). If `t`
  were the time the event occurred, **every retry after the tolerance window would be permanently
  unverifiable**: the receiver would reject precisely the deliveries retries are meant to complete,
  and the failure would look like a signing error rather than a clock one.

  Therefore, **each delivery attempt is signed afresh, with `t` set at the moment that attempt
  leaves the dispatcher.** A redelivery carries a *different* `t` and a *different* `v1`, while
  carrying the **same** `X-BBSign-Event-Id`. The roles are split: `t` proves freshness of the
  *attempt* and `X-BBSign-Event-Id` identifies the *event*. Conflating them defeats either replay
  protection or retries.

  As a result, the dispatcher does not compute the signature once and store it with the delivery
  row: it computes it on every attempt.
</Aside>

- `v1` may appear **more than once** during secret rotation. A receiver **must** accept the payload if
  **any** `v1` value matches. Verifiers that read only the first `v1` prevent rotation.
- Unknown schemes **must** be ignored, not rejected. This allows a future `v2` to be introduced
  without affecting existing receivers.

## 3. What is signed

```text
signed_string = <t> + "." + <raw_request_body>
signature     = HMAC-SHA256(key = subscription_secret, message = signed_string)
v1            = lowercase hex encoding of signature   // 64 chars
```

- **`<t>` is the same value as in the header.** Signing it is what prevents replay; signing the
  body alone is not enough.
- **`raw_request_body` is the exact bytes received**, before any parsing, re-serialization or
  charset conversion. Not a re-encoded object, and not a reformatted version.
- Encoding is **lowercase hex**, not base64. Receivers should compare case-insensitively.
- The body is UTF-8 JSON, but verification is defined over **bytes**, not text.

<Aside type="caution" title="Keep the raw body">
  Most web frameworks discard the raw bytes when they parse JSON. `JSON.stringify(req.body)` is
  **not** the raw body: key order, whitespace and numeric formatting differ, and the HMAC does not
  match.

  - **Express**: `express.json({ verify: (req,_res,buf) => { req.rawBody = buf } })`
  - **Next.js (app router)**: `await req.text()` before `JSON.parse`
  - **Fastify**: `addContentTypeParser` retaining the buffer
  - **Spring**: `ContentCachingRequestWrapper`, or a `@RequestBody byte[]`

  Both SDK pages show how to do this in each ecosystem.
</Aside>

## 4. Tolerance window

<strong><Fact of={WEBHOOKS.toleranceSeconds} unit="seconds" />.</strong> Normative, not suggested.

A receiver rejects the delivery when `abs(now - t) > 300`. The window is symmetric, to tolerate
clock skew in both directions.

<Aside type="note" title="Verifiers must accept an injectable clock">
  A vector with a fixed `t` falls outside the window minutes after it is written. Without an
  injectable clock, every positive vector would eventually become a failure **indistinguishable
  from the expired-timestamp negative**, and the suite would keep passing without testing anything.

  Both SDKs therefore expose the window and the current time as optional parameters, defaulting to
  the tolerance above and "now":

  - Java: `Webhooks.verify(signature, body, secret, Duration tolerance, Instant now)`, with a
    three-argument overload delegating to `(..., Duration.ofSeconds(300), Instant.now())`
  - JavaScript: `verifyWebhookSignature(signature, body, secret, { toleranceSeconds = 300, nowSeconds = Date.now()/1000 })`

  The three-argument form is what a customer uses. The clock-bearing form is what the vectors run
  against, and it is part of the public API, not a test-only facility.
</Aside>

## 5. Verification algorithm

Receivers perform, in order:

1. Parse the header. Malformed: **return false** (section 6).
2. Extract `t`; non-integer: return false.
3. Check `abs(now - t) <= 300`; else return false.
4. Compute the expected signature over `<t> + "." + raw_body`.
5. Compare against **each** `v1` using a **constant-time** comparison. Any match: true.

**Constant-time comparison is mandatory.** A byte-wise early-exit compare reveals the correct
signature prefix over repeated attempts.

- Java: `MessageDigest.isEqual`
- Node: `crypto.timingSafeEqual`

## 5b. Public helper signatures (normative)

Both SDKs expose the same shape, so anyone familiar with one can read the other:

| | Java | JavaScript |
|---|---|---|
| Simple | `Webhooks.verify(String signature, byte[] body, String secret)` | `verifyWebhookSignature(signature, body, secret)`; the options bag **must** default (`opts = {}`), or the three-arg form throws |
| With clock | `Webhooks.verify(sig, body, secret, Duration tolerance, Instant now)` | `verifyWebhookSignature(sig, body, secret, { toleranceSeconds, nowSeconds })` |
| Returns | `boolean` | `boolean` |
| Throws | never (section 6) | never (section 6) |
| Constant-time primitive | `MessageDigest.isEqual` | `crypto.timingSafeEqual` |

`body` is **bytes**, not a parsed object; see section 3.

## 6. Failure contract: verifiers never throw

`verify(...)` **returns a boolean and does not throw on any input.** Malformed headers are under a
potential attacker's control, and a thrown exception is both a 500 in the customer's route and a
side channel.

Specifically:

| Input | Required behaviour |
|---|---|
| Missing or empty header | `false` |
| Header with no `t` or no `v1` | `false` |
| `t` not an integer | `false` |
| `t` textually an integer but **out of range** (`t=99999999999999999999`) | `false`. Java's `Long.parseLong` **throws** where JS `Number()` silently returns a float; this lands squarely inside the never-throws contract and the languages diverge by default. Parse defensively and bound `t` to a sane epoch range |
| `v1` not 64 hex chars | `false`; **validate shape before decoding** |
| Odd-length or non-hex `v1` | `false`. Note `Buffer.from(x,'hex')` **silently truncates** invalid input, and `timingSafeEqual` **throws** on length mismatch. Both must be handled before the compare |
| Correct shape, wrong value | `false` |
| Expired timestamp | `false` |

## 7. Test vectors

**Location: <a href="/sync/sign/webhook-signature-vectors.json">webhook-signature-vectors.json</a>**,
the file both SDKs and the server are tested against, unchanged. Neither SDK defines its own
vectors: with different vectors, two SDKs could disagree with each other and still each pass their
own tests.

Format:

```json
{
  "version": 1,
  "cases": [
    {
      "name": "valid-signature",
      "secret": "<base64>",
      "bodyUtf8": "{\"eventId\":\"...\",\"type\":\"envelope.completed\"}",
      "header": "t=1754400000,v1=<hex>",
      "now": 1754400060,
      "expected": true
    }
  ]
}
```

**Field contract: all five are required, and there is no sixth.**

| Field | Meaning |
|---|---|
| `name` | case identifier |
| `secret` | base64; decode to bytes before use as the HMAC key |
| `bodyUtf8` | the request body **as a UTF-8 string**; implementations encode it to bytes. Named for the encoding because section 3 defines signing over bytes and "body" alone left it ambiguous |
| `header` | the **literal** `X-BBSign-Signature` value, not structured fields. This is what makes rotation and whitespace cases expressible |
| `now` | the clock value passed to the verifier (section 4) |
| `expected` | boolean |

**There is deliberately no separate `timestamp` field.** An earlier draft included one alongside
`header`, and an implementation that read `timestamp` instead of parsing `header` would have passed
every vector and still failed on **real deliveries**. The only source of `t` is the header.

Required cases, <Fact of={WEBHOOKS.testVectorCount} /> in all; every implementation runs all of them:

| Case | `expected` |
|---|---|
| valid signature, fresh timestamp | `true` |
| valid, at exactly `+300s` | `true` |
| valid, at +301s | `false` |
| valid, at -301s | `false` |
| tampered body, one byte changed | `false` |
| wrong secret | `false` |
| two `v1` values, second one correct (rotation) | `true` |
| unknown scheme `v2=` present alongside valid `v1` | `true` |
| header with whitespace after commas | `true` |
| missing header | `false` |
| missing `t` | `false` |
| `v1` not hex | `false` |
| `v1` wrong length | `false` |
| empty body | per vector |
| body with non-ASCII UTF-8 | `true` |
| `t` out of numeric range | `false` |

## 8. Comparison with Adobe Acrobat Sign

Adobe verifies a webhook by requiring the endpoint to echo `X-AdobeSign-ClientId` at registration,
and **does not sign payloads**. bb-sign signs every delivery, so the receiver can verify its origin
and integrity even if the URL becomes known to third parties.

[Migrating from Adobe Acrobat Sign](/en/sign/developers/migrating-from-adobe/) describes this
difference for teams that are migrating.

## 9. Changing this document

The scheme is frozen. A change means a new scheme identifier (`v2=`) emitted alongside `v1` during
a deprecation window, never a redefinition of `v1`. This is possible because receivers ignore
unknown schemes (section 2).

## Part 2. The event payload

**Status: NORMATIVE.** Part 1 establishes that the payload takes precedence over the header; this
part defines the payload. An explicitly defined payload gives customers a stable contract: they
receive the information they need to act, and internal changes in bb-sign do not alter what
reaches their endpoint.

### P1. The outbound payload is a deliberate DTO, never the internal event

The dispatcher maps each internal event to a `WebhookEvent` DTO owned by the public surface. No
internal class reaches the wire. Adding a field to an internal event has **no** effect on
customers unless the DTO is also changed; that separation is the purpose of the design.

### P2. Envelope

Every delivery has the same outer shape, so a receiver can route it before parsing the details:

```json
{
  "id": "3f8c1c2e-7d0a-4f3b-9d2a-0a1b2c3d4e5f",
  "type": "envelope.completed",
  "apiVersion": "2026-08-09",
  "createdAt": "2026-08-09T14:22:31Z",
  "data": { }
}
```

| Field | Notes |
|---|---|
| `id` | Matches the `X-BBSign-Event-Id` header exactly. Stable across redeliveries; the dedup key |
| `type` | Public event name. **No `.v1` suffix**; the internal event type is not this field |
| `apiVersion` | Dated contract stamp. **Informational only in v1**: a subscription has no version field, so a receiver cannot pin one and this cannot behave as a negotiated version. It tells a receiver which contract produced the payload |
| `createdAt` | When the **event** occurred. Distinct from the signature's `t`, which is when this *attempt* was sent (section 2) |
| `data` | Per-type, below |

`orgId` is deliberately **omitted**: a subscription belongs to exactly one org, so including it
would give the receiver no new information and would expose an internal identifier in every
payload.

### P3. Event types and their `data`

There are {WEBHOOK_EVENTS.length} today. Names are public and stable; they are **not** the internal
routing keys. New types may be added: a receiver ignores one it does not know (P4).

| `type` | `data` |
|---|---|
| `envelope.sent` | `envelope` |
| `envelope.completed` | `envelope` + the completion notice fields (P3a) + `retention` (P3c) |
| `envelope.cancelled` | `envelope` |
| `envelope.expired` | `envelope` |
| `signer.signed` | `envelope` + `signer` |
| `signer.viewed` | `envelope` + `signer` |
| `envelope.evidence_issued` | `envelope` + the completion notice fields (P3a). It follows an `envelope.completed` that went out without the certificate |
| `document.restored` | `envelope` + `document`: a restore of an archived file ended |

```json
"data": {
  "envelope": {
    "id": "uuid", "title": "string", "status": "SENT|COMPLETED|CANCELLED|EXPIRED",
    "createdAt": "iso8601", "expiresAt": "iso8601|null"
  },
  "signer": {
    "id": "uuid", "email": "string", "name": "string",
    "signOrder": 1, "status": "PENDING|SIGNED", "signedAt": "iso8601|null",
    "authMethod": "EMAIL_LINK|EMAIL_LINK_OTP|null"
  }
}
```

`signer.authMethod` says how the signer was identified when they signed: `EMAIL_LINK` (the link
only) or `EMAIL_LINK_OTP` (the link plus a one-time code sent by email). It is `null` before they
sign, and for signatures made before the field existed. More values may be added.

`document.restored` carries `data.document = {id, kind, outcome, reason, availableUntil, downloadPath}`:

- `kind` is `ORIGINAL` or `SIGNED`. `outcome` is `RESTORED` (readable until `availableUntil`),
  `AVAILABLE` (it never needed a restore) or `FAILED`, with `reason` `DELETED`, `TIMEOUT` or
  `STORAGE_ERROR` (`null` otherwise).
- `downloadPath` is always `/api/v1/envelopes/{id}/documents`, the same resource as
  `documentsPath`: call it with `document:download` for the file's availability and a short-lived
  link. **No URL is ever in the payload.**
- One event per restore, whoever asked; its `id` is deterministic for each restore. An integration
  that requests a restore through the API is told only this way: API credentials are never emailed.

This is enough to act on without an additional call, which is the purpose of a webhook.
**Deliberately excluded:** document content and download URLs (a presigned URL in a payload stays
usable after delivery), `ipAddress` and `userAgent` from the signing events (internal data), and
any field not listed in this part. Fields ending in `Path` are API paths you call with the token,
not links.

<Aside type="tip" title="How a customer gets the signed document">
  When you receive `envelope.completed`, **call `GET /api/v1/envelopes/{id}/documents`**: it is
  org-scoped, part of the published surface, and returns `signedUrl` once the envelope is
  `COMPLETED`. Short-lived links fetched on demand are safer than long-lived ones embedded in a
  payload that may end up stored in logs.
</Aside>

### P3a. The completion notice

**One `envelope.completed` per envelope and subscription** is sent, on whichever comes first:

- the evidence certificate is issued (`evidenceStatus: ISSUED`, with `evidenceCertificate`);
- it is late (`PENDING`, after <Fact of={EVIDENCE.degradedAfterHours} unit="hours" />) or could
  not be produced (`FAILED`);
- the envelope will never have one (`UNAVAILABLE`: it completed while certificates were not being
  issued).

No notice is withheld more than <Fact of={EVIDENCE.degradedClampHours} unit="hours" />. A notice
sent without the certificate is followed by **`envelope.evidence_issued`** when the certificate
arrives (never after `UNAVAILABLE`). Subscribe to it to receive a late certificate.

```json
"data": {
  "envelope": { ... },
  "evidenceStatus": "ISSUED|PENDING|FAILED|UNAVAILABLE",
  "signedDocumentsStatus": "READY|PREPARING",
  "documents": [ { "documentId": "uuid", "filename": "string", "originalSha256": "hex|null", "signedSha256": "hex|null" } ],
  "documentsPath": "/api/v1/envelopes/{id}/documents",
  "evidenceCertificate": { "evidenceId": "uuid", "sha256": "hex", "auditTrailSha256": "hex", "language": "es|en",
                           "downloadPath": "/api/v1/envelopes/{id}/evidence-certificate/download" },
  "auditChainHead": { "seq": 12, "hash": "hex",
                      "auditCoverage": { "level": "FULL|PARTIAL", "fullRows": 12, "partialRows": 0, "lastPartialAt": null,
                                         "reasons": [], "migratedAt": null } }
}
```

- These fields are on `envelope.completed` and `envelope.evidence_issued` only, and absent on an
  `envelope.completed` sent before they existed. Absent means `null`.
- `evidenceCertificate` and `auditChainHead` are present only when `evidenceStatus` is `ISSUED`. A
  notice reports the state **when it was sent**: a later certificate arrives as
  `envelope.evidence_issued`, never as a second `envelope.completed`.
- **`signedDocumentsStatus: PREPARING`** (the signed copies did not exist yet): treat
  `documents[].signedSha256` as unknown, do not compare or store a hash, and download the signed
  documents later from `documentsPath`.
- `evidenceStatus` may gain values: treat an unknown one like `PENDING`.
- **A `PENDING` notice may never be followed by anything.** If the certificate then fails, no
  webhook says so; `envelope.evidence_issued` arrives only if a later re-issue succeeds. A receiver
  that must know the outcome reads `GET /api/v1/envelopes/{id}/evidence-certificate` (its `status`)
  some days later, rather than waiting for an event.
- The certificate is fetched on demand from `downloadPath` (JSON with a link valid for
  <Fact of={EVIDENCE.downloadLinkSeconds} unit="s" />), never carried in the payload, for the reason
  given in P3.

### P3c. Retention dates on `envelope.completed`

Every `envelope.completed`, with or without the certificate, carries the dates of the envelope's
fixed retention (<Fact of={RETENTION_POLICY.retentionDays} unit="days" />):

```json
"data": {
  "envelope": { ... },
  "retention": { "archivesAt": "2027-01-16T00:00:00Z|null", "deletesAt": "2027-10-16T00:00:00Z" }
}
```

- Both dates are rounded up to 00:00 UTC, and they are the **earliest** any file of the envelope
  reaches. `GET documentsPath` gives each file's exact dates (`original.deletesAt`,
  `signed.deletesAt`).
- **`deletesAt` means "no longer available from"**: from that date the files cannot be downloaded,
  and they are erased permanently within the following days. Archive what you must keep before it.
- `archivesAt` is when the files may move to archive storage, from where they are restored on
  request. It is always present, and `null` until archiving is enabled.{!RETENTION_IMPLEMENTED.documentsArchiveTransitionLive.value && ' It is not enabled in production today.'}
- `retention` is on `envelope.completed` only, and absent on one sent before it existed.
- The body is materialised once (P3b), so a notice keeps the dates it was sent with. Each file's
  current dates are always on `GET documentsPath`.

### P3b. The body is materialised once, not per attempt

If the body were rendered on every attempt, the same `X-BBSign-Event-Id` could carry **different
bytes** across retries: an `envelope.sent` retried after the envelope completed would report
`status: COMPLETED`, a state that did not exist when the event was emitted, and a receiver
deduplicating on event id would arbitrarily keep the first copy received.

**The body is rendered at first dispatch and stored verbatim on the delivery row. Every retry resends
those exact bytes.** Only the signature is recomputed per attempt (section 2: `t` is attempt time;
the body is event time). A redelivery is **byte-identical**, not merely same-event-id.

### P3d. `data` is read from current state at render time

The internal events carry only identifiers, so the dispatcher loads the envelope (and, for
`signer.*`, the signer) at render time. Because rendering reads current state, P3b pins it to first
dispatch. (In the source specification this section is also numbered P3c.)

### P4. Additive-only

Receivers **must** ignore unknown fields. New fields and event types may appear without an
`apiVersion` change; a subscription receives only the types it selected. Removing a field or
changing its type breaks the contract and produces a new `apiVersion`.
