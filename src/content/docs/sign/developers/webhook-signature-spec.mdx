**Estado: NORMATIVO.** Este documento es la fuente única de verdad del esquema de firma de
webhooks de bb-sign. El dispatcher, el SDK de Java y el SDK de JavaScript lo implementan y remiten
a esta página. La parte 1 define cómo se firma una entrega; la parte 2 define su contenido.

## 1. Encabezados

| Header | Valor | Notas |
|---|---|---|
| `X-BBSign-Signature` | `t=<unix-seconds>,v1=<hex>` | Ver la gramática en la sección 2 |
| `X-BBSign-Event-Id` | UUID v4 | **Estable en cada reenvío del mismo evento.** La clave de deduplicación del receptor |
| `X-BBSign-Event-Type` | p. ej. `envelope.completed` | Informativo; el payload prevalece sobre este encabezado |

## 2. Gramática del encabezado de firma

```text
signature-header = element *( "," element )
element          = scheme "=" value
scheme           = "t" / "v1" / <future scheme>
```

- Los elementos van separados por comas **sin espacios**. Los receptores **deben** tolerar
  espacios de todos modos.
- `t` aparece exactamente una vez: **segundos** Unix, en base 10, sin parte fraccionaria.

<Aside type="caution" title="t es la hora de envío del intento, no la hora del evento">
  La secuencia de reintentos dura aproximadamente
  <Fact of={WEBHOOKS.retryLadderHoursApprox} unit="horas" />, mientras que la ventana de tolerancia
  es de <Fact of={WEBHOOKS.toleranceSeconds} unit="s" /> (sección 4). Si `t` fuera la hora en que
  ocurrió el evento, **todo reintento posterior a la ventana de tolerancia sería permanentemente
  inverificable**: el receptor rechazaría justamente las entregas que los reintentos deben hacer
  llegar, y el fallo aparentaría ser un error de firma y no de reloj.

  Por tanto, **cada intento de entrega se firma de nuevo, con `t` fijado en el momento en que ese
  intento sale del dispatcher.** Un reenvío lleva un `t` *distinto* y un `v1` *distinto*, pero el
  **mismo** `X-BBSign-Event-Id`. Así se reparten las funciones: `t` prueba la vigencia del
  *intento* y `X-BBSign-Event-Id` identifica el *evento*. Confundirlos anula la protección contra
  reproducción o los reintentos.

  En consecuencia, el dispatcher no calcula la firma una sola vez para guardarla con la fila de la
  entrega: la calcula en cada intento.
</Aside>

- `v1` puede aparecer **más de una vez** durante la rotación del secreto. Un receptor **debe**
  aceptar el payload si **cualquier** valor `v1` coincide. Los verificadores que leen solo el primer
  `v1` impiden la rotación.
- Los esquemas desconocidos **deben** ignorarse, no rechazarse. Esto permite introducir un futuro
  `v2` sin afectar a los receptores existentes.

## 3. Qué se firma

```text
signed_string = <t> + "." + <raw_request_body>
signature     = HMAC-SHA256(key = subscription_secret, message = signed_string)
v1            = lowercase hex encoding of signature   // 64 chars
```

- **`<t>` es el mismo valor que va en el encabezado.** Firmarlo es lo que impide la reproducción;
  firmar solo el cuerpo no basta.
- **`raw_request_body` son los bytes exactos recibidos**, antes de cualquier interpretación,
  reserialización o conversión de juego de caracteres. No un objeto recodificado ni una versión
  reformateada.
- La codificación es **hex en minúsculas**, no base64. Los receptores deberían comparar sin
  distinguir mayúsculas.
- El cuerpo es JSON UTF-8, pero la verificación se define sobre **bytes**, no sobre texto.

<Aside type="caution" title="Conservar el cuerpo original">
  La mayoría de los frameworks web descartan los bytes originales al interpretar el JSON.
  `JSON.stringify(req.body)` **no** es el cuerpo original: el orden de las claves, los espacios y
  el formato numérico difieren, y el HMAC no coincide.

  - **Express**: `express.json({ verify: (req,_res,buf) => { req.rawBody = buf } })`
  - **Next.js (app router)**: `await req.text()` antes de `JSON.parse`
  - **Fastify**: `addContentTypeParser` conservando el buffer
  - **Spring**: `ContentCachingRequestWrapper`, o un `@RequestBody byte[]`

  Las páginas de ambos SDKs muestran cómo hacerlo en cada ecosistema.
</Aside>

## 4. Ventana de tolerancia

<strong><Fact of={WEBHOOKS.toleranceSeconds} unit="segundos" />.</strong> Normativa, no sugerida.

Un receptor rechaza la entrega cuando `abs(now - t) > 300`. La ventana es simétrica, para tolerar
desfases de reloj en ambas direcciones.

<Aside type="note" title="Los verificadores deben aceptar un reloj inyectable">
  Un vector con un `t` fijo queda fuera de la ventana minutos después de escribirse. Sin un reloj
  inyectable, cada vector positivo terminaría convirtiéndose en un fallo **indistinguible del caso
  negativo de marca de tiempo expirada**, y la suite seguiría aprobando sin probar nada.

  Por eso ambos SDKs exponen la ventana y la hora actual como parámetros opcionales, con la
  tolerancia de arriba y «ahora» como valores por defecto:

  - Java: `Webhooks.verify(signature, body, secret, Duration tolerance, Instant now)`, con una
    sobrecarga de tres argumentos que delega en `(..., Duration.ofSeconds(300), Instant.now())`
  - JavaScript: `verifyWebhookSignature(signature, body, secret, { toleranceSeconds = 300, nowSeconds = Date.now()/1000 })`

  La forma de tres argumentos es la que usa un cliente. La forma con reloj es la que ejecutan los
  vectores, y forma parte de la API pública, no es un recurso exclusivo de pruebas.
</Aside>

## 5. Algoritmo de verificación

Los receptores ejecutan, en orden:

1. Interpretar el encabezado. Si está mal formado: **devolver false** (sección 6).
2. Extraer `t`; si no es un entero: devolver false.
3. Comprobar `abs(now - t) <= 300`; en caso contrario, devolver false.
4. Calcular la firma esperada sobre `<t> + "." + raw_body`.
5. Comparar con **cada** valor `v1` mediante una comparación en **tiempo constante**. Si alguno coincide: true.

**La comparación en tiempo constante es obligatoria.** Una comparación byte a byte con salida
temprana revela el prefijo correcto de la firma a lo largo de intentos repetidos.

- Java: `MessageDigest.isEqual`
- Node: `crypto.timingSafeEqual`

## 5b. Firmas públicas de los helpers (normativo)

Ambos SDKs exponen la misma forma, de modo que quien conoce uno puede leer el otro:

| | Java | JavaScript |
|---|---|---|
| Simple | `Webhooks.verify(String signature, byte[] body, String secret)` | `verifyWebhookSignature(signature, body, secret)`; la bolsa de opciones **debe** tener valor por defecto (`opts = {}`), o la forma de tres argumentos lanza una excepción |
| Con reloj | `Webhooks.verify(sig, body, secret, Duration tolerance, Instant now)` | `verifyWebhookSignature(sig, body, secret, { toleranceSeconds, nowSeconds })` |
| Devuelve | `boolean` | `boolean` |
| Lanza | nunca (sección 6) | nunca (sección 6) |
| Primitiva de tiempo constante | `MessageDigest.isEqual` | `crypto.timingSafeEqual` |

`body` son **bytes**, no un objeto parseado; ver la sección 3.

## 6. Contrato de fallo: los verificadores nunca lanzan excepciones

`verify(...)` **devuelve un booleano y no lanza excepciones con ninguna entrada.** Los encabezados
mal formados están bajo control de un posible atacante, y una excepción lanzada es a la vez un 500
en la ruta del cliente y un canal lateral.

En concreto:

| Entrada | Comportamiento requerido |
|---|---|
| Header ausente o vacío | `false` |
| Header sin `t` o sin `v1` | `false` |
| `t` no es un entero | `false` |
| `t` textualmente entero pero **fuera de rango** (`t=99999999999999999999`) | `false`. `Long.parseLong` de Java **lanza una excepción** donde `Number()` de JS devuelve en silencio un flotante; esto cae de lleno dentro del contrato de nunca lanzar, y los lenguajes divergen por defecto. Interprete el valor de forma defensiva y acote `t` a un rango de época razonable |
| `v1` no tiene 64 caracteres hex | `false`; **valida la forma antes de decodificar** |
| `v1` de longitud impar o no hex | `false`. Tenga en cuenta que `Buffer.from(x,'hex')` **trunca en silencio** la entrada inválida, y `timingSafeEqual` **lanza una excepción** si las longitudes no coinciden. Ambos casos deben manejarse antes de comparar |
| Forma correcta, valor incorrecto | `false` |
| Marca de tiempo caducada | `false` |

## 7. Vectores de prueba

**Ubicación: <a href="/sync/sign/webhook-signature-vectors.json">webhook-signature-vectors.json</a>**,
el archivo contra el que se prueban ambos SDKs y el servidor, sin cambios. Ningún SDK define
vectores propios: con vectores distintos, dos SDKs podrían discrepar entre sí y aun así aprobar
cada uno sus pruebas.

Formato:

```json
{
  "version": 1,
  "cases": [
    {
      "name": "valid-signature",
      "secret": "<base64>",
      "bodyUtf8": "{\"eventId\":\"...\",\"type\":\"envelope.completed\"}",
      "header": "t=1754400000,v1=<hex>",
      "now": 1754400060,
      "expected": true
    }
  ]
}
```

**Contrato de campos: los cinco son obligatorios, y no hay un sexto.**

| Campo | Significado |
|---|---|
| `name` | identificador del caso |
| `secret` | base64; se decodifica a bytes antes de usarlo como clave HMAC |
| `bodyUtf8` | el cuerpo de la petición **como cadena UTF-8**; las implementaciones lo codifican a bytes. Se llama así por la codificación, porque la sección 3 define la firma sobre bytes y «body» a solas lo dejaba ambiguo |
| `header` | el valor **literal** de `X-BBSign-Signature`, no campos estructurados. Esto es lo que permite expresar los casos de rotación y de espacios |
| `now` | el valor de reloj que se pasa al verificador (sección 4) |
| `expected` | booleano |

**No existe un campo `timestamp` separado, de forma deliberada.** Un borrador anterior lo incluía
junto a `header`, y una implementación que leyera `timestamp` en lugar de interpretar `header`
habría aprobado todos los vectores y aun así fallado con **entregas reales**. La única fuente de
`t` es el encabezado.

Casos obligatorios, <Fact of={WEBHOOKS.testVectorCount} /> en total; cada implementación los ejecuta todos:

| Caso | `expected` |
|---|---|
| firma válida, marca de tiempo fresca | `true` |
| válida, exactamente a `+300s` | `true` |
| válida, a +301s | `false` |
| válida, a -301s | `false` |
| cuerpo manipulado, un byte cambiado | `false` |
| secreto incorrecto | `false` |
| dos valores `v1`, el segundo correcto (rotación) | `true` |
| esquema desconocido `v2=` presente junto a un `v1` válido | `true` |
| header con espacios después de las comas | `true` |
| header ausente | `false` |
| falta `t` | `false` |
| `v1` no es hex | `false` |
| `v1` con longitud incorrecta | `false` |
| cuerpo vacío | según el vector |
| cuerpo con UTF-8 no ASCII | `true` |
| `t` fuera del rango numérico | `false` |

## 8. Comparación con Adobe Acrobat Sign

Adobe verifica un webhook exigiendo que el endpoint devuelva `X-AdobeSign-ClientId` al
registrarlo, y **no firma los payloads**. bb-sign firma cada entrega, de modo que el receptor puede
comprobar su origen e integridad aunque la URL sea conocida por terceros.

[Migrar desde Adobe Acrobat Sign](/sign/developers/migrating-from-adobe/) describe esta diferencia
para quienes migran.

## 9. Cambiar este documento

El esquema está congelado. Un cambio implica un nuevo identificador de esquema (`v2=`) emitido
junto a `v1` durante una ventana de deprecación, nunca una redefinición de `v1`. Esto es posible
porque los receptores ignoran los esquemas desconocidos (sección 2).

## Parte 2. El payload del evento

**Estado: NORMATIVO.** La parte 1 establece que el payload prevalece sobre el encabezado; esta
parte define el payload. Un payload definido de forma explícita da a los clientes un contrato
estable: reciben la información necesaria para actuar, y los cambios internos de bb-sign no
alteran lo que llega a su endpoint.

### P1. El payload de salida es un DTO deliberado, nunca el evento interno

El dispatcher convierte cada evento interno en un DTO `WebhookEvent` que pertenece a la
superficie pública. Ninguna clase interna llega a la red. Agregar un campo a un evento interno
**no** tiene efecto sobre los clientes, salvo que también se modifique el DTO; esa separación es
el propósito del diseño.

### P2. Envoltorio

Cada entrega tiene la misma forma externa, para que un receptor pueda enrutarla antes de
interpretar los detalles:

```json
{
  "id": "3f8c1c2e-7d0a-4f3b-9d2a-0a1b2c3d4e5f",
  "type": "envelope.completed",
  "apiVersion": "2026-08-09",
  "createdAt": "2026-08-09T14:22:31Z",
  "data": { }
}
```

| Campo | Notas |
|---|---|
| `id` | Coincide exactamente con el header `X-BBSign-Event-Id`. Estable entre reenvíos; la clave de deduplicación |
| `type` | Nombre público del evento. **Sin sufijo `.v1`**; el tipo interno del evento no es este campo |
| `apiVersion` | Sello fechado del contrato. **Solo informativo en v1**: una suscripción no tiene campo de versión, así que un receptor no puede fijar una y esto no puede comportarse como una versión negociada. Le dice al receptor qué contrato produjo el payload |
| `createdAt` | Cuándo ocurrió el **evento**. Distinto del `t` de la firma, que es cuándo se envió este *intento* (sección 2) |
| `data` | Por tipo, abajo |

`orgId` se **omite** de forma deliberada: una suscripción pertenece a una única organización, de
modo que incluirlo no aportaría información al receptor y expondría un identificador interno en
cada payload.

### P3. Tipos de evento y su `data`

Hoy son {WEBHOOK_EVENTS.length}. Los nombres son públicos y estables; **no** corresponden a las
claves internas de enrutamiento. Pueden añadirse tipos nuevos: un receptor ignora los que no conoce
(P4).

| `type` | `data` |
|---|---|
| `envelope.sent` | `envelope` |
| `envelope.completed` | `envelope` + los campos del aviso de finalización (P3a) + `retention` (P3c) |
| `envelope.cancelled` | `envelope` |
| `envelope.expired` | `envelope` |
| `signer.signed` | `envelope` + `signer` |
| `signer.viewed` | `envelope` + `signer` |
| `envelope.evidence_issued` | `envelope` + los campos del aviso de finalización (P3a). Llega después de un `envelope.completed` que se envió sin el certificado |
| `document.restored` | `envelope` + `document`: terminó la restauración de un archivo archivado |

```json
"data": {
  "envelope": {
    "id": "uuid", "title": "string", "status": "SENT|COMPLETED|CANCELLED|EXPIRED",
    "createdAt": "iso8601", "expiresAt": "iso8601|null"
  },
  "signer": {
    "id": "uuid", "email": "string", "name": "string",
    "signOrder": 1, "status": "PENDING|SIGNED", "signedAt": "iso8601|null",
    "authMethod": "EMAIL_LINK|EMAIL_LINK_OTP|null"
  }
}
```

`signer.authMethod` indica cómo se identificó al firmante al firmar: `EMAIL_LINK` (solo el enlace) o
`EMAIL_LINK_OTP` (el enlace y un código de un solo uso enviado por correo). Es `null` antes de que
firme y en las firmas anteriores a este campo. Pueden añadirse valores.

`document.restored` lleva `data.document = {id, kind, outcome, reason, availableUntil, downloadPath}`:

- `kind` es `ORIGINAL` o `SIGNED`. `outcome` es `RESTORED` (se lee hasta `availableUntil`),
  `AVAILABLE` (nunca necesitó restauración) o `FAILED`, con `reason` `DELETED`, `TIMEOUT` o
  `STORAGE_ERROR` (`null` en los demás casos).
- `downloadPath` es siempre `/api/v1/envelopes/{id}/documents`, el mismo recurso que
  `documentsPath`: consúltelo con `document:download` para obtener la disponibilidad del archivo y un
  enlace de corta duración. **El payload nunca lleva una URL.**
- Un evento por restauración, la haya pedido quien la haya pedido; su `id` es determinista para cada
  restauración. Una integración que pide una restauración por la API se entera solo así: las
  credenciales de API nunca reciben correos.

Esta información basta para actuar sin una llamada adicional, que es el propósito de un webhook.
**Se excluyen de forma deliberada:** el contenido de los documentos y las URL de descarga (una URL
prefirmada dentro de un payload sigue siendo útil después de la entrega), `ipAddress` y
`userAgent` de los eventos de firma (datos internos) y cualquier campo no listado en esta parte. Los
campos que terminan en `Path` son rutas de la API que se consultan con el token, no enlaces.

<Aside type="tip" title="Cómo obtiene un cliente el documento firmado">
  Al recibir `envelope.completed`, **llame a `GET /api/v1/envelopes/{id}/documents`**: tiene
  alcance de organización, forma parte de la superficie publicada y devuelve `signedUrl` cuando el
  sobre está `COMPLETED`. Los enlaces de corta duración obtenidos bajo demanda son más seguros que
  los de larga duración incluidos en un payload que puede quedar guardado en registros.
</Aside>

### P3a. El aviso de finalización

Se envía **un solo `envelope.completed` por sobre y suscripción**, con lo primero que ocurra:

- se emite el certificado de evidencia (`evidenceStatus: ISSUED`, con `evidenceCertificate`);
- el certificado se retrasa (`PENDING`, pasadas <Fact of={EVIDENCE.degradedAfterHours} unit="horas" />)
  o no se pudo producir (`FAILED`);
- el sobre nunca tendrá certificado (`UNAVAILABLE`: se completó mientras no se emitían certificados).

Ningún aviso se retiene más de <Fact of={EVIDENCE.degradedClampHours} unit="horas" />. Un aviso
enviado sin el certificado va seguido de **`envelope.evidence_issued`** cuando el certificado llega
(nunca después de `UNAVAILABLE`). Suscríbase a ese evento para recibir un certificado tardío.

```json
"data": {
  "envelope": { ... },
  "evidenceStatus": "ISSUED|PENDING|FAILED|UNAVAILABLE",
  "signedDocumentsStatus": "READY|PREPARING",
  "documents": [ { "documentId": "uuid", "filename": "string", "originalSha256": "hex|null", "signedSha256": "hex|null" } ],
  "documentsPath": "/api/v1/envelopes/{id}/documents",
  "evidenceCertificate": { "evidenceId": "uuid", "sha256": "hex", "auditTrailSha256": "hex", "language": "es|en",
                           "downloadPath": "/api/v1/envelopes/{id}/evidence-certificate/download" },
  "auditChainHead": { "seq": 12, "hash": "hex",
                      "auditCoverage": { "level": "FULL|PARTIAL", "fullRows": 12, "partialRows": 0, "lastPartialAt": null,
                                         "reasons": [], "migratedAt": null } }
}
```

- Estos campos están solo en `envelope.completed` y `envelope.evidence_issued`, y faltan en un
  `envelope.completed` enviado antes de que existieran. Un campo ausente equivale a `null`.
- `evidenceCertificate` y `auditChainHead` están presentes solo cuando `evidenceStatus` es `ISSUED`.
  Un aviso informa el estado **del momento en que se envió**: un certificado posterior llega como
  `envelope.evidence_issued`, nunca como un segundo `envelope.completed`.
- **`signedDocumentsStatus: PREPARING`** (las copias firmadas aún no existían): trate
  `documents[].signedSha256` como desconocido, no compare ni guarde un hash y descargue los
  documentos firmados más tarde desde `documentsPath`.
- `evidenceStatus` puede ganar valores: trate uno desconocido como `PENDING`.
- **Un aviso `PENDING` puede no tener continuación.** Si después el certificado falla, ningún webhook
  lo informa; `envelope.evidence_issued` llega solo si una reemisión posterior tiene éxito. Un
  receptor que necesite conocer el resultado consulta `GET /api/v1/envelopes/{id}/evidence-certificate`
  (su `status`) unos días después, en lugar de esperar un evento.
- El certificado se obtiene bajo demanda en `downloadPath` (un JSON con un enlace válido durante
  <Fact of={EVIDENCE.downloadLinkSeconds} unit="s" />), nunca dentro del payload, por la razón
  indicada en P3.

### P3c. Fechas de conservación en `envelope.completed`

Todo `envelope.completed`, con o sin certificado, lleva las fechas del plazo fijo de conservación del
sobre (<Fact of={RETENTION_POLICY.retentionDays} unit="días" />):

```json
"data": {
  "envelope": { ... },
  "retention": { "archivesAt": "2027-01-16T00:00:00Z|null", "deletesAt": "2027-10-16T00:00:00Z" }
}
```

- Ambas fechas se redondean hacia arriba a las 00:00 UTC y son las **más tempranas** que alcanza
  cualquier archivo del sobre. `GET documentsPath` da las fechas exactas de cada archivo
  (`original.deletesAt`, `signed.deletesAt`).
- **`deletesAt` significa «deja de estar disponible el»**: desde esa fecha los archivos no se pueden
  descargar y se borran de forma definitiva en los días siguientes. Archive antes lo que deba
  conservar.
- `archivesAt` es la fecha desde la que los archivos pueden pasar a almacenamiento de archivo, desde
  donde se restauran a pedido. Está siempre presente y vale `null` mientras el archivo no esté
  habilitado.{!RETENTION_IMPLEMENTED.documentsArchiveTransitionLive.value && ' Hoy no lo está en producción.'}
- `retention` está solo en `envelope.completed`, y falta en uno enviado antes de que existiera.
- El cuerpo se materializa una vez (P3b), de modo que un aviso conserva las fechas con las que se
  envió. Las fechas actuales de cada archivo están siempre en `GET documentsPath`.

### P3b. El cuerpo se materializa una vez, no por intento

Si el cuerpo se generara en cada intento, un mismo `X-BBSign-Event-Id` podría llevar **bytes
distintos** a lo largo de los reintentos: un `envelope.sent` reintentado después de completarse el
sobre informaría `status: COMPLETED`, un estado que no existía cuando se emitió el evento, y un
receptor que elimina duplicados por id de evento conservaría arbitrariamente la primera copia
recibida.

**El cuerpo se renderiza en el primer envío y se guarda tal cual en la fila de la entrega. Cada
reintento reenvía exactamente esos bytes.** Solo la firma se recalcula por intento (sección 2: `t`
es la hora del intento; el cuerpo es la hora del evento). Un reenvío es **idéntico byte a byte**,
no solo del mismo id de evento.

### P3d. `data` se lee del estado actual al renderizar

Los eventos internos llevan solo identificadores, de modo que el dispatcher carga el sobre (y,
para `signer.*`, el firmante) al renderizar. Como el renderizado lee el estado actual, P3b lo fija
al primer envío. (En la especificación de origen, esta sección también se numera P3c.)

### P4. Solo aditivo

Los receptores **deben** ignorar los campos desconocidos. Pueden aparecer campos y tipos de
evento nuevos sin cambiar `apiVersion`; una suscripción recibe solo los tipos que seleccionó.
Eliminar un campo o cambiar su tipo rompe el contrato y genera un nuevo `apiVersion`.
