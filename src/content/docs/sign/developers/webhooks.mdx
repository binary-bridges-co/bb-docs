Con los webhooks, bb-sign envía un payload JSON firmado a su URL cada vez que ocurre algo en un
sobre, y su sistema reacciona al instante sin consultas periódicas.

El esquema de firma se define de forma normativa en la
[especificación de firma de webhooks](/sign/developers/webhook-signature-spec/); esta página es la
guía de integración.

## Registrar un webhook

En **Configuración**, pestaña **Webhooks**, seleccione **Nuevo webhook**.

- **URL del endpoint**: «Debe ser HTTPS y accesible desde internet. Rechazamos direcciones
  privadas e internas». La validación se repite en cada entrega.
- **Eventos que quieres recibir**: seleccione los que necesite entre los {WEBHOOK_EVENTS.length} disponibles:

| Evento | Cuándo |
|---|---|
| `envelope.sent` | Un sobre se envió a sus firmantes |
| `envelope.completed` | Todos los firmantes firmaron. Se envía una sola vez, con el certificado de evidencia si está listo a tiempo |
| `envelope.cancelled` | Un sobre se canceló |
| `envelope.expired` | Un sobre llegó a su fecha de vencimiento sin completarse |
| `signer.signed` | Un firmante firmó; otros pueden estar pendientes |
| `signer.viewed` | Un firmante abrió el documento |
| `envelope.evidence_issued` | El certificado de evidencia llegó después de un `envelope.completed` que se envió sin él |
| `document.restored` | Terminó la restauración de un archivo archivado (ver [Conservación y restauración](#conservación-y-restauración)) |

Pueden añadirse tipos de evento nuevos: su receptor debe ignorar los que no conoce. Una suscripción
recibe solo los tipos que seleccionó.

El **secreto de firma se muestra una sola vez**, al crear el webhook. Guárdelo en su gestor de
secretos. Una organización puede tener hasta <Fact of={WEBHOOKS.maxPerOrg} /> webhooks.

## Contenido de la entrega

```json
{
  "id": "3f8c...",
  "type": "envelope.completed",
  "apiVersion": "2026-08-09",
  "createdAt": "2026-08-09T14:22:31Z",
  "data": {
    "envelope": {
      "id": "...", "title": "Q3 Agreement", "status": "COMPLETED",
      "createdAt": "...", "expiresAt": null
    },
    "signer": { "id": "...", "email": "...", "name": "...", "signOrder": 1, "status": "SIGNED", "signedAt": "...", "authMethod": "EMAIL_LINK_OTP" }
  }
}
```

`data.envelope` está en todos los eventos. Los demás campos de `data` dependen del tipo:

| Campo | Eventos | Contenido |
|---|---|---|
| `signer` | `signer.*` | El firmante. `signer.authMethod` indica cómo se identificó al firmar: `EMAIL_LINK` (solo el enlace) o `EMAIL_LINK_OTP` (el enlace y un código de un solo uso enviado por correo). Es `null` antes de firmar y en las firmas anteriores a este campo |
| `evidenceStatus`, `signedDocumentsStatus`, `documents`, `documentsPath`, `evidenceCertificate`, `auditChainHead` | `envelope.completed`, `envelope.evidence_issued` | El aviso de finalización: el estado del certificado de evidencia, el SHA-256 de cada documento (original y firmado) y, cuando el certificado está emitido, sus hashes y la ruta para descargarlo |
| `retention` | `envelope.completed` | Las fechas de conservación del sobre (ver [Conservación y restauración](#conservación-y-restauración)) |
| `document` | `document.restored` | El archivo cuya restauración terminó y su resultado |

Pueden aparecer campos nuevos dentro de un mismo `apiVersion`: ignore los que no conozca. Los
esquemas completos figuran en la [referencia de la API](/sign/api/) como `WebhookEvent`, de modo
que un cliente generado los recibe tipados. La
[especificación](/sign/developers/webhook-signature-spec/#p3a-el-aviso-de-finalización) detalla
cada campo.

Cada entrega incluye tres encabezados:

| Encabezado | Uso |
|---|---|
| `X-BBSign-Signature` | La firma que se verifica. `t=<unix>,v1=<hex>` |
| `X-BBSign-Event-Id` | Su **clave de idempotencia**, estable entre reintentos |
| `X-BBSign-Event-Type` | El nombre del evento, para enrutar antes de interpretar el cuerpo |

### Obtener el documento firmado

Al recibir `envelope.completed`, llame a `GET /api/v1/envelopes/{id}/documents` (la ruta llega en
`data.documentsPath`) para obtener los archivos. La respuesta incluye `signedUrl` cuando el sobre
está `COMPLETED`, válido durante <Fact of={ENVELOPE.downloadUrlSeconds} unit="s" />. El payload no
incluye enlaces de descarga a propósito: un enlace prefirmado dentro del payload seguiría siendo
útil después de la entrega y podría quedar guardado en registros. Los campos que terminan en `Path`
son rutas de la API que se consultan con el token, no enlaces.

Para guardar una copia completa y comprobada de cada sobre:

1. Suscríbase a `envelope.completed` y a `envelope.evidence_issued` (el certificado que llega tarde).
2. Descargue cada documento desde `data.documentsPath`. El SHA-256 del PDF firmado debe coincidir con
   `data.documents[].signedSha256`. Si `signedDocumentsStatus` es `PREPARING`, ese hash todavía no
   se conoce: no lo compare y descargue los documentos más tarde.
3. Llame a `data.evidenceCertificate.downloadPath`: devuelve un enlace al
   [certificado de evidencia](/sign/concepts/evidence-certificate/) válido durante
   <Fact of={EVIDENCE.downloadLinkSeconds} unit="s" />. El SHA-256 del PDF debe coincidir con
   `data.evidenceCertificate.sha256`.
4. Guarde `data.retention.deletesAt`: desde esa fecha, bb-sign ya no tiene los archivos.

El [recorrido completo](/sign/developers/envelope-walkthrough/) muestra toda la secuencia en curl,
JavaScript y Java.

## Verificar la firma sobre el cuerpo original

**La firma cubre los bytes exactos recibidos.** La mayoría de los frameworks web interpretan el
JSON antes de entregarlo al handler, y volver a serializar ese objeto produce *bytes distintos*
(cambian el orden de las claves y los espacios), por lo que la verificación falla aunque el objeto
sea correcto. Capture el cuerpo original antes de cualquier interpretación.

<Tabs syncKey="lang">
  <TabItem label="JavaScript">
    ```js
    import { verifyWebhookSignature } from '@binarybridges/bb-sign-sdk/webhooks'

    app.use(express.json({ verify: (req, _res, buf) => { req.rawBody = buf } }))

    app.post('/webhooks/bb-sign', (req, res) => {
      if (!verifyWebhookSignature(req.get('X-BBSign-Signature'), req.rawBody, SECRET)) {
        return res.sendStatus(401)
      }
      res.sendStatus(200)
      void handle(JSON.parse(req.rawBody.toString('utf8')))
    })
    ```

    En Next.js, use `await request.text()` en lugar de `.json()`. En Fastify, registre un parser de
    content-type con `parseAs: 'buffer'`. La página del [SDK de JavaScript](/sign/sdks/javascript/)
    incluye ambos ejemplos completos.
  </TabItem>
  <TabItem label="Java">
    ```java
    @PostMapping("/webhooks/bb-sign")
    public ResponseEntity<Void> receive(
            @RequestHeader("X-BBSign-Signature") String signature,
            @RequestBody byte[] rawBody) throws IOException {   // byte[], NOT a DTO

        if (!Webhooks.verify(signature, rawBody, System.getenv("BBSIGN_WEBHOOK_SECRET"))) {
            return ResponseEntity.status(401).build();
        }
        WebhookEvent event = MAPPER.readValue(rawBody, WebhookEvent.class);
        // ... handle asynchronously
        return ResponseEntity.ok().build();
    }
    ```

    `MAPPER` es el `ObjectMapper` que se muestra en la página del [SDK de Java](/sign/sdks/java/),
    configurado para fechas ISO-8601 y para ignorar los campos nuevos. Esa página explica también
    por qué el parámetro es `byte[]`.
  </TabItem>
</Tabs>

### Implementar un verificador propio

La [especificación](/sign/developers/webhook-signature-spec/) es normativa y breve. Tres requisitos
merecen atención especial:

1. **Comparar en tiempo constante.** Un `==` sobre el digest revela, byte a byte, qué parte de una
   firma falsificada es correcta, y eso basta para construir una válida.
2. **Comprobar la marca de tiempo.** Sin comprobación de vigencia, una entrega capturada podría
   reenviarse indefinidamente.
3. **Aceptar cualquier `v1` que coincida.** Durante una rotación del secreto, el encabezado lleva
   dos valores; exigir que coincida el primero anula la ventana de rotación.

Los <a href="/sync/sign/webhook-signature-vectors.json">vectores de prueba</a> incluyen
<Fact of={WEBHOOKS.testVectorCount} /> casos, entre ellos los que deben *fallar*. El servidor y
ambos SDKs se prueban contra ese mismo archivo; pruebe también su verificador contra él.

## Entrega y reintentos

**Responda 2xx de inmediato y procese después.** Confirme la recepción en cuanto la firma sea
válida y procese el evento de forma asíncrona.

**Reintentos.** Una entrega fallida se reintenta con una secuencia de esperas que abarca
aproximadamente <Fact of={WEBHOOKS.retryLadderHoursApprox} unit="horas" />, con esperas de
<code>{WEBHOOKS.retryLadder.value.join(', ')}</code>. Cualquier 2xx
cuenta como éxito; cualquier otra respuesta, como fallo.

**Desactivación automática.** Tras <Fact of={WEBHOOKS.disableAfterLadders} /> entregas
consecutivas que agotan sus reintentos, la suscripción se desactiva y los administradores de la
organización reciben un correo. El panel muestra el estado **Desactivado automáticamente**, con la
nota: «Desactivamos este endpoint después de que sus reintentos fallaran repetidamente. Corrígelo
y vuelve a activarlo». bb-sign también prueba el endpoint cada
<Fact of={WEBHOOKS.probeIntervalHours} unit="horas" />, y una respuesta exitosa lo reactiva.

**Eventos durante la desactivación.** Se registran como **No enviado** y no se acumulan para
después, de modo que su sistema no recibe una avalancha de eventos antiguos al reactivarse. El
historial muestra exactamente qué eventos no se entregaron.

**Entrega al menos una vez.** Un mismo evento puede llegar dos veces, por ejemplo tras un corte de
red o un reinicio. `X-BBSign-Event-Id` es idéntico en ambos casos; úselo para eliminar duplicados.

**Cuerpo estable entre reintentos.** El cuerpo se genera una sola vez y se reenvía byte por byte,
de modo que un `envelope.sent` reintentado horas después describe el momento del envío. Solo se
recalcula la firma, porque incluye la hora de entrega.

## Consultar el historial de entregas

En **Configuración**, pestaña **Webhooks**, **Historial** muestra cada evento, cada intento, el
código de respuesta y el error. Las entradas se conservan durante
<Fact of={WEBHOOKS.deliveryLogRetentionDays} unit="días" />. Es el primer lugar para diagnosticar
una entrega:

| Estado | Significado | Acción |
|---|---|---|
| Entregado | El evento llegó y su endpoint respondió 2xx | Ninguna |
| Rechazado / Inaccesible | Su endpoint respondió con error o no respondió; la lista de intentos indica cuál | Revise sus registros para ese intento; el siguiente reintento ya está programado |
| Abandonado | Se agotaron los reintentos | Corrija el endpoint y consulte el estado del sobre con la API; este evento no se reenvía |
| No enviado | El endpoint estaba desactivado en ese momento | Active el endpoint y concilie el periodo con `GET /api/v1/envelopes` |
| No se pudo construir | Un error del lado de bb-sign | Contacte a soporte |

## Conservación y restauración

bb-sign conserva cada archivo de un sobre durante un plazo fijo de
<Fact of={RETENTION_POLICY.retentionDays} unit="días" />: el original desde su subida, la copia
firmada desde la finalización y el certificado de evidencia desde su emisión. Las fechas se redondean
a las 00:00 UTC.

- **`deletesAt`** (en `data.retention` de `envelope.completed` y en cada archivo de
  `GET /api/v1/envelopes/{id}/documents`) significa «deja de estar disponible el»: desde esa fecha
  los archivos no se pueden descargar y se borran de forma definitiva en los días siguientes.
  Archive antes lo que deba conservar.
- **`archivesAt`** es la fecha desde la que un archivo puede pasar a almacenamiento de archivo. Los
  términos del servicio lo permiten desde el día <Fact of={RETENTION_POLICY.archiveAfterDays} />.
  {!RETENTION_IMPLEMENTED.documentsArchiveTransitionLive.value && <>Hoy ningún archivo se mueve a almacenamiento de archivo, de modo que <code>archivesAt</code> es <code>null</code> y todos los archivos se descargan directamente.</>}
- El cuerpo de una entrega se fija en el primer envío. Las fechas actuales de cada archivo están
  siempre en `GET /api/v1/envelopes/{id}/documents`.

**Restaurar un archivo archivado.** `GET /api/v1/envelopes/{id}/documents` informa la disponibilidad
de cada archivo en `original.availability` y `signed.availability`:

| Valor | Significado |
|---|---|
| `AVAILABLE`, `RESTORED` | Se puede descargar |
| `ARCHIVED` | Está en almacenamiento de archivo: pida su restauración |
| `RESTORE_IN_PROGRESS` | Se está restaurando |
| `DELETED` | Superó su plazo de conservación |

Pida un archivo con `POST /api/v1/envelopes/{id}/documents/{docId}/restore` y el cuerpo
`{"kind": "SIGNED"}` (o `"ORIGINAL"`). Responde `202` mientras se restaura, por lo general en unas
horas, y `200` si el archivo no necesita restauración. Aunque lo pidan varias personas, se ejecuta
una sola restauración. La copia restaurada se descarga durante
<Fact of={RESTORE.days} unit="días" />. Una organización puede tener como máximo
<Fact of={RESTORE.maxActivePerOrg} /> restauraciones en curso. El ciclo completo se describe en
[Conservación y restauración](/sign/sending/retention-and-restore/).

**Una integración se entera solo por `document.restored`**: las credenciales de API nunca reciben
correos. Si su integración pide restauraciones, suscríbase a ese evento. Llega un evento por
restauración, también por las que pidió una persona o un firmante:

```json
"data": {
  "envelope": { "id": "...", "title": "...", "status": "COMPLETED", "createdAt": "...", "expiresAt": null },
  "document": {
    "id": "...", "kind": "SIGNED", "outcome": "RESTORED", "reason": null,
    "availableUntil": "2027-03-02T14:05:00Z", "downloadPath": "/api/v1/envelopes/{id}/documents"
  }
}
```

- `outcome` es `RESTORED` (se descarga hasta `availableUntil`), `AVAILABLE` (nunca necesitó
  restauración) o `FAILED`, con `reason` `DELETED` (superó su plazo), `TIMEOUT` (tardó demasiado:
  pídala de nuevo) o `STORAGE_ERROR`. Pueden añadirse valores.
- El payload no lleva enlaces: consulte `downloadPath` para obtener la disponibilidad y un enlace de
  corta duración.

## Rotar el secreto

En **Configuración**, pestaña **Webhooks**, seleccione **Rotar secreto**. «Se aceptarán tanto el
secreto antiguo como el nuevo durante un periodo de gracia, así que tu receptor seguirá
funcionando hasta que lo despliegues con el nuevo». El periodo de gracia es de
<Fact of={WEBHOOKS.secretRotationGraceHours} unit="horas" />. Las entregas en esa ventana llevan
dos valores `v1`; un verificador correcto acepta cualquiera de los dos, como hacen ambos SDKs.

## Probar el endpoint

**Enviar prueba** entrega un evento sintético a su endpoint y muestra el código de estado de la
respuesta. Usa el mismo proceso de firma que las entregas reales, de modo que valida su
verificador de extremo a extremo.
