El SDK de JavaScript conecta sus servicios de Node con la API de bb-sign: gestiona los tokens,
reintenta de forma segura y verifica las firmas de los webhooks. El paquete es
<code><Fact of={SDK.js.packageName} /></code>, versión <Fact of={SDK.js.version} />.

**Requiere Node <Fact of={SDK.js.minNode} /> o superior y es solo ESM.** Use `import`; `require()`
no está soportado.

## Instalación

El SDK se entrega como el tarball <code><Fact of={SDK.js.tarball} /></code>, generado con
`npm pack`. Instálelo en su proyecto:

```bash
npm install ../path/to/binarybridges-bb-sign-sdk-0.1.0.tgz
```

## Inicio rápido

Las credenciales se crean en **Configuración**, pestaña **Credenciales de API**, de bb-sign; el
secreto se muestra una sola vez, al crearlas. Léalas desde variables de entorno, fuera del código
fuente.

```js
import { createClient } from '@binarybridges/bb-sign-sdk'

const client = createClient({
  baseUrl: process.env.BBSIGN_BASE_URL,
  tokenUrl: process.env.BBSIGN_TOKEN_URL,
  clientId: process.env.BBSIGN_CLIENT_ID,
  clientSecret: process.env.BBSIGN_CLIENT_SECRET,
})

const envelope = await client.envelopes.createEnvelope({
  createEnvelopeRequest: {
    title: 'Q3 Agreement',
    otpRequired: false,
    expiresAt: new Date(Date.now() + 72 * 3600 * 1000),
    signers: [{ email: 'signer@example.com', name: 'A Signer', signOrder: 1 }],
  },
})

console.log('Created', envelope.id)
```

Los tokens se obtienen, se guardan en caché y se renuevan automáticamente. Las llamadas
concurrentes comparten una sola solicitud de token.

### Qué cubre el cliente

El cliente expone `envelopes`, `documents` y `verification`:

| Acceso | Operaciones |
|---|---|
| `envelopes` | Crear, listar, consultar, adjuntar documentos, agregar firmantes, enviar, cancelar, contar por estado, listar los documentos con sus enlaces y `restoreEnvelopeDocument` (pedir la restauración de un archivo archivado) |
| `documents` | `uploadDocument`. Los métodos generados envían JSON, de modo que una subida multipart se hace con `fetch` (ver el [recorrido completo](/sign/developers/envelope-walkthrough/#2-subir-el-documento)) |
| `verification` | `verifyDocument` (el sello del código QR) y `verifyDocumentFile` (ver [Comprobar un archivo](#comprobar-un-archivo)) |

**No están en el cliente** el certificado de evidencia, `GET /api/v1/workspaces` ni las copias de
acuerdos: el paquete no exporta sus clases y `createClient` no las expone. Llámelas con `fetch` y un
token obtenido como en el [recorrido completo](/sign/developers/envelope-walkthrough/#1-obtener-un-token);
el paso 8 de ese recorrido descarga el certificado de evidencia.

### Listar por páginas

```js
for await (const envelope of client.eachPage(
  (page) => client.envelopes.listEnvelopes({ page, size: 50 }),
  (p) => p.content,
)) {
  console.log(envelope.title)
}
```

Las páginas se obtienen bajo demanda, de modo que recorrer miles de sobres no los carga todos en
memoria.

## Verificar un webhook

<Aside type="caution" title="Solo en el servidor">
  Este helper usa su **secreto de firma de webhooks**. Se importa desde una ruta aparte,
  <code><Fact of={SDK.js.webhookSubpath} /></code>, que no tiene build para navegador: un bundler
  orientado al navegador no la resuelve, por diseño. Así el secreto nunca termina en un bundle
  público.
</Aside>

```js
import { verifyWebhookSignature } from '@binarybridges/bb-sign-sdk/webhooks'
```

### Capturar el cuerpo original

La firma cubre **los bytes exactos recibidos**. Los frameworks de Node más usados interpretan el
JSON por defecto y entregan un objeto; volver a serializarlo produce bytes distintos y la
verificación falla aunque el objeto sea correcto. Capture el cuerpo original como se muestra a
continuación.

**Express**

```js
import express from 'express'

app.use(express.json({
  verify: (req, _res, buf) => { req.rawBody = buf },   // keep the bytes
}))

app.post('/webhooks/bb-sign', (req, res) => {
  if (!verifyWebhookSignature(req.get('X-BBSign-Signature'), req.rawBody, SECRET)) {
    return res.sendStatus(401)
  }
  const event = JSON.parse(req.rawBody.toString('utf8'))
  res.sendStatus(200)                                   // ack first, work after
  void handle(event)
})
```

**Next.js (App Router)**

```js
export async function POST(request) {
  const rawBody = await request.text()                  // text(), not json()
  if (!verifyWebhookSignature(request.headers.get('x-bbsign-signature'), rawBody, SECRET)) {
    return new Response(null, { status: 401 })
  }
  const event = JSON.parse(rawBody)
  return new Response(null, { status: 200 })
}
```

**Fastify**: registre un parser de content-type que conserve el buffer:

```js
fastify.addContentTypeParser('application/json', { parseAs: 'buffer' }, (req, body, done) => {
  req.rawBody = body
  done(null, JSON.parse(body.toString('utf8')))
})
```

El helper acepta un `string` o un `Buffer`. **Un objeto ya interpretado produce un error de
tipos**, en lugar de convertirse en silencio con `JSON.stringify`, que daría bytes distintos de los
firmados.

### Resultado booleano, sin excepciones

El helper recibe datos que pueden venir de un atacante. Por eso devuelve siempre un booleano: una
excepción produciría un 500 en su ruta de webhook y revelaría por qué falló la verificación.

### Responder de inmediato y procesar después

Devuelva 2xx en cuanto la firma sea válida. bb-sign reintenta con una secuencia que abarca
aproximadamente <Fact of={WEBHOOKS.retryLadderHoursApprox} unit="horas" />, y tras
<Fact of={WEBHOOKS.disableAfterLadders} /> secuencias consecutivas agotadas **desactiva el
endpoint**. Procese el evento de forma asíncrona para que la respuesta no dependa de la carga.

### Eliminar duplicados por id de evento

`X-BBSign-Event-Id` es estable entre reintentos y reentregas. La entrega es al menos una vez; use
este valor como clave de idempotencia.

### Rotación del secreto

Mientras la ventana de rotación está abierta, el encabezado lleva dos valores `v1=` y cualquiera de
los dos verifica. Esto le permite desplegar el nuevo secreto sin interrupción, sin configuración
adicional.

### Probar el handler

La verificación depende del tiempo: una firma con más de
<Fact of={WEBHOOKS.toleranceSeconds} unit="s" /> de antigüedad se rechaza, de modo que un fixture
fijo deja de ser válido. Fije el reloj en las pruebas:

```js
verifyWebhookSignature(header, rawBody, secret, { nowSeconds: 1760000000 })
```

Un receptor detrás de una cola puede ampliar la ventana con `toleranceSeconds`.

## Comprobar un archivo

`verification.verifyDocumentFile` envía los bytes de un PDF a `POST /api/v1/verify/file`, que calcula
su SHA-256 en el servidor y responde si es un documento firmado por bb-sign. La ruta es pública, no
guarda el archivo y acepta hasta <Fact of={VERIFY.fileMaxMb} unit="MB" />, con un límite de
<Fact of={RATE_LIMITS.verifyFilePerMinutePerClient} /> solicitudes por minuto por cliente.

```js
import { openAsBlob } from 'node:fs'

const result = await client.verification.verifyDocumentFile({
  body: await openAsBlob('contract-signed.pdf', { type: 'application/octet-stream' }),
})
console.log(result.match, result.sha256)
```

Solo coinciden los PDF firmados: un original sin firmar nunca coincide. `verifyDocument`, en cambio,
comprueba el sello impreso en el código QR contra los registros de bb-sign y no lee el PDF.

## Reintentos

Las solicitudes `GET` se reintentan ante errores 5xx y fallos de transporte, con backoff
exponencial y jitter completo, desde <Fact of={SDK.retryBaseMs} unit="ms" /> y como máximo
<Fact of={SDK.retryMaxBackoffMs} unit="ms" />.

**Un `POST` cuya respuesta no se recibió no se reintenta.** Si `createEnvelope` agota el tiempo de
espera, el resultado es desconocido: el sobre puede existir ya, y un reintento crearía un segundo
acuerdo enviado a las mismas personas. La API no usa claves de idempotencia. El SDK de Java se
comporta igual.

Si una creación agota el tiempo de espera, **liste antes de reintentar**:

```js
try {
  await client.envelopes.createEnvelope({ createEnvelopeRequest: request })
} catch (error) {
  if (error.statusCode === 0) {
    // Never reached bb-sign, or the answer was lost. Check before sending again.
  }
}
```

`429` y `503` se reintentan también en `POST`, porque indican que el servidor no procesó la
solicitud. El SDK **no respeta `Retry-After`**: ante un `RATE_LIMITED`, sus reintentos llegan
antes de que se abra la ventana y fallan de nuevo. Si recibe <code>{QUOTA.httpStatusWhenExhausted.value}</code>,
espere los segundos de `Retry-After` antes de volver a llamar; esa espera queda a cargo de su código.

## Errores

Cada fallo lanza un `BbSignError` con un `statusCode`. `0` indica que la solicitud no obtuvo
respuesta.{SDK.errorCarriesStatusOnly.value && <> El error lleva solo el estado, no el cuerpo ni su <code>code</code>: si necesita el <code>code</code>, haga esa llamada por HTTP y lea el cuerpo.</>}

| Estado | Significado |
|---|---|
| 400 | Solicitud mal formada o con errores de validación |
| 401 | Credenciales rechazadas. El SDK renueva y reintenta una vez antes de reportarlo |
| 403 | Autenticado, pero esta credencial no tiene el permiso de la organización |
| 404 | El recurso no existe, o pertenece a otra organización o a un espacio de trabajo que la credencial no puede ver. No se distinguen, de forma intencional |
| 408 | La subida a la verificación por archivo superó el tiempo máximo |
| 409 | El recurso no está en un estado que permita la operación |
| 410 | El archivo que se pide restaurar ya superó su plazo de conservación |
| 413 | El archivo enviado a la verificación supera el tamaño máximo |
| 429 | El servidor no procesó la solicitud: una cuota agotada (`QUOTA_EXCEEDED`), un límite de tasa (`RATE_LIMITED`) o demasiadas restauraciones en curso (`RESTORE_LIMIT_REACHED`) |
| 503 | Un servicio del que depende la operación no respondió |

El error contiene un estado y un mensaje, **sin** el objeto `Response`: registrarlo en un log no
expone su encabezado `Authorization`. Tampoco trae el cuerpo, de modo que un 429 por cuota y uno
por límite de tasa se ven iguales; si necesita el `code`, haga esa llamada con `fetch` y lea el
cuerpo. Los mensajes nunca incluyen su secreto, aunque la respuesta
de bb-sign lo contenga. [Errores](/sign/developers/errors/) incluye la tabla completa y el cuerpo
del error.

## Novedades del contrato

El SDK se genera a partir del contrato OpenAPI, de modo que una entrega actual ya tiene tipados los
campos que se agregaron desde la primera:

- `EnvelopeResponse`: `archived`, `archivedAt`, `retention` y `restoresInProgress`.
- `DocumentWithUrlsResponse`: `originalSha256`, y `original` y `signed` (`DocumentFile`, con
  `availability`, `deletesAt`, `archivesAt`, `availableUntil` y `restorable`).
- `WebhookEventData`: `evidenceStatus`, `signedDocumentsStatus`, `documents`, `documentsPath`,
  `evidenceCertificate`, `auditChainHead`, `retention` y `document`; `WebhookEventSigner.authMethod`.
- Los tipos de evento `envelope.evidence_issued` y `document.restored`.

Un evento de un tipo que su código no conoce debe ignorarse: pueden añadirse tipos nuevos.

## Versiones

La versión es <Fact of={SDK.js.version} />. Las entregas posteriores conservaron ese número aunque
agregaron operaciones y campos, de modo que la versión no basta para saber qué tarball tiene. Si
no está seguro de tener la entrega actual, pídala antes de integrar los campos de esta página.

## Garantías de seguridad

- **Credenciales fuera de los logs.** El SDK no tiene hook de logging que pueda registrarlas.
- **TLS siempre verificado.** La verificación de certificados no se puede desactivar.
- **Escrituras sin duplicados.** Una escritura con resultado desconocido no se reintenta (ver
  [Reintentos](#reintentos)).
- **Secreto de webhooks solo en el servidor.** El helper de webhooks no se puede empaquetar para
  navegador, por diseño.

## Compilar desde el código fuente

```bash
cd sdk-js
npm install
npm run generate     # regenerates src/generated from docs/api/openapi.json
npm run build
npm test
./verify.sh          # the CI gate: drift, browser-bundle refusal, any-leaks, pack contents
npm pack             # produces binarybridges-bb-sign-sdk-0.1.0.tgz
```

`src/generated/` es **código generado y versionado**: regenérelo en lugar de editarlo.
`GENERATION.md`, en el código fuente del SDK, documenta la configuración del generador.
