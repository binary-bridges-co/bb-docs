El SDK de Java conecta sus servicios con la API de bb-sign: gestiona los tokens, reintenta de
forma segura y verifica las firmas de los webhooks. Las coordenadas son
<code><Fact of={SDK.java.groupId} />:<Fact of={SDK.java.artifactId} />:<Fact of={SDK.java.version} /></code>.
Esta página reúne el `README.md` del SDK y su `README-INSTALL.md`.

Requiere **Java <Fact of={SDK.java.minJava} />** o superior.

## Instalación

El SDK se entrega en cuatro archivos: el jar, su pom, un `.sha256` y la guía de instalación. También
puede compilarlo desde el código fuente (ver [Compilar desde el código fuente](#compilar-desde-el-código-fuente)).
Instale el jar en su repositorio local de Maven y declárelo como dependencia.

<Steps>
1. Verifique la integridad del archivo recibido, y que el `.sha256` sea el de la entrega más reciente
   (ver [Versiones](#versiones)):

   ```bash
   shasum -a 256 -c bb-sign-sdk-java-0.1.0-SNAPSHOT.jar.sha256
   ```

2. Instálelo. **`-DpomFile` es obligatorio:**

   ```bash
   mvn install:install-file \
     -Dfile=bb-sign-sdk-java-0.1.0-SNAPSHOT.jar \
     -DpomFile=bb-sign-sdk-java-0.1.0-SNAPSHOT.pom
   ```

3. Declárelo como dependencia:

   ```xml
   <dependency>
     <groupId>co.binarybridges.sign</groupId>
     <artifactId>bb-sign-sdk-java</artifactId>
     <version>0.1.0-SNAPSHOT</version>
   </dependency>
   ```
</Steps>

<Aside type="caution" title="Incluya siempre -DpomFile">
  Sin este parámetro, Maven genera un pom sin dependencias. La instalación y la compilación terminan
  sin errores, pero la primera llamada a la API falla en tiempo de ejecución con
  `NoClassDefFoundError` para una clase de Retrofit o de okhttp. El pom es el que declara okhttp,
  Retrofit y Jackson. Si aparece ese error, reinstale con `-DpomFile`.
</Aside>

### Dependencias

**El build debe tener acceso a Maven Central.** El SDK es un jar simple, no shaded: su build
resuelve okhttp, Retrofit y Jackson y los unifica con las versiones que ya usa. Esto evita
conflictos con Jackson, presente en la mayoría de los servicios Java.

Si su build no tiene acceso a Maven Central, contáctenos antes de comenzar la integración para
recibir una variante shaded del SDK.

## Inicio rápido

El ejemplo completo cabe en un solo archivo. Las credenciales se crean en **Configuración**,
pestaña **Credenciales de API**, de bb-sign; el secreto se muestra una sola vez, al crearlas.

```java
import co.binarybridges.sign.sdk.BbSignClient;
import co.binarybridges.sign.sdk.generated.model.*;
import java.time.OffsetDateTime;
import java.util.List;

try (BbSignClient client = BbSignClient.builder()
        .baseUrl(System.getenv("BBSIGN_BASE_URL"))
        .tokenUrl(System.getenv("BBSIGN_TOKEN_URL"))
        .clientCredentials(System.getenv("BBSIGN_CLIENT_ID"), System.getenv("BBSIGN_CLIENT_SECRET"))
        .build()) {

    CreateEnvelopeRequest request = new CreateEnvelopeRequest()
            .title("Q3 Agreement")
            .otpRequired(false)
            .expiresAt(OffsetDateTime.now().plusHours(72))
            .signers(List.of(new CreateSignerSpec()
                    .email("signer@example.com")
                    .name("A Signer")
                    .signOrder(1)));

    EnvelopeResponse envelope = client.execute(client.envelopes().createEnvelope(request));
    System.out.println("Created " + envelope.getId());
}
```

Lea las credenciales desde variables de entorno, fuera del código fuente. El secreto se almacena
solo en Keycloak y bb-sign no conserva copia; si se pierde, rótelo, lo que invalida el anterior
**de inmediato**.

### Qué cubre el cliente

El cliente expone `envelopes()`, `documents()` y `verification()`:

| Acceso | Operaciones |
|---|---|
| `envelopes()` | Crear, listar, consultar, adjuntar documentos, agregar firmantes, enviar, cancelar, contar por estado, listar los documentos con sus enlaces y `restoreEnvelopeDocument` (pedir la restauración de un archivo archivado) |
| `documents()` | `uploadDocument`. Los métodos generados envían JSON, de modo que una subida multipart se hace con okhttp (ver el [recorrido completo](/sign/developers/envelope-walkthrough/#2-subir-el-documento)) |
| `verification()` | `verifyDocument` (el sello del código QR) y `verifyDocumentFile`, que **hoy no funciona**: ver [Comprobar un archivo](#comprobar-un-archivo) |

**No están en el cliente** el certificado de evidencia, `GET /api/v1/workspaces` ni las copias de
acuerdos. Sus interfaces se generan, pero `BbSignClient` no las expone. Llámelas por HTTP con un token
obtenido como en el [recorrido completo](/sign/developers/envelope-walkthrough/#1-obtener-un-token); el
paso 8 de ese recorrido descarga el certificado de evidencia en Java.

### Listar por páginas

```java
client.eachPage(
        page -> client.envelopes().listEnvelopes(page, 50, null, null, null, null, null, null),
        PagedEnvelopeResponse::getContent)
    .forEach(envelope -> System.out.println(envelope.getTitle()));
```

Las páginas se obtienen bajo demanda durante la iteración, de modo que recorrer miles de sobres no
los carga todos en memoria.

## Verificar un webhook

`Webhooks.verify` comprueba la firma sobre el cuerpo tal como se recibió. Declare el cuerpo como
`byte[]` en su handler, y lea el evento con un `ObjectMapper` configurado como el del SDK:

```java
import co.binarybridges.sign.sdk.Webhooks;
import co.binarybridges.sign.sdk.generated.model.WebhookEvent;
import com.fasterxml.jackson.databind.DeserializationFeature;
import com.fasterxml.jackson.databind.ObjectMapper;
import com.fasterxml.jackson.datatype.jsr310.JavaTimeModule;

// ISO-8601 dates (JavaTimeModule), and new fields ignored instead of fatal.
private static final ObjectMapper MAPPER = new ObjectMapper()
        .registerModule(new JavaTimeModule())
        .disable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES);

@PostMapping("/webhooks/bb-sign")
public ResponseEntity<Void> receive(
        @RequestHeader("X-BBSign-Signature") String signature,
        @RequestBody byte[] rawBody) throws IOException {   // byte[], NOT a DTO

    if (!Webhooks.verify(signature, rawBody, System.getenv("BBSIGN_WEBHOOK_SECRET"))) {
        return ResponseEntity.status(401).build();
    }

    WebhookEvent event = MAPPER.readValue(rawBody, WebhookEvent.class);
    switch (event.getType()) {
        case ENVELOPE_COMPLETED -> onCompleted(event.getData());
        case SIGNER_SIGNED      -> onSigned(event.getData().getSigner());
        default                 -> { /* ignore other types, UNKNOWN_DEFAULT_OPEN_API included */ }
    }
    return ResponseEntity.ok().build();
}
```

`event.getType()` devuelve el enum `WebhookEvent.TypeEnum`, no un `String`, de modo que los `case`
usan sus constantes. Un `new ObjectMapper()` sin configurar no sirve: no lee las fechas
(`OffsetDateTime`) y falla ante cualquier campo nuevo, y el contrato agrega campos sin cambiar de
versión. <code>{SDK.java.jsr310Dependency.value}</code> ya es una dependencia del SDK, en la versión
<Fact of={SDK.java.jacksonVersion} /> de Jackson que declara su pom.

<Aside type="caution" title="Use la entrega actual del SDK">
  Un tipo de evento que el SDK no conoce se lee como `UNKNOWN_DEFAULT_OPEN_API`. Las entregas
  anteriores de
  <code><Fact of={SDK.java.version} /></code>, con el mismo número de versión, lanzan una excepción
  ante un tipo nuevo como `envelope.evidence_issued` o `document.restored`. Compruebe el `.sha256`
  con el de la entrega más reciente.
</Aside>

### Capturar el cuerpo original

La firma cubre **los bytes exactos recibidos**. Si el parámetro se declara como un DTO, Spring
interpreta el JSON y entrega un objeto; volver a serializarlo produce bytes distintos (cambian el
orden de las claves y los espacios) y la verificación falla aunque el objeto sea correcto.

- **Spring MVC**: `@RequestBody byte[]` o `@RequestBody String`, o un `ContentCachingRequestWrapper`
  si además necesita la forma interpretada.
- **Jakarta Servlet**: lea `request.getInputStream()` una sola vez, antes que cualquier otro
  componente.

El SDK recibe `byte[]` en lugar de `String` de forma intencional: el tipo orienta hacia el uso
correcto.

### Responder de inmediato y procesar después

Devuelva 2xx en cuanto la firma sea válida y procese el evento de forma asíncrona. bb-sign
reintenta con una secuencia que abarca aproximadamente
<Fact of={WEBHOOKS.retryLadderHoursApprox} unit="horas" />, y tras
<Fact of={WEBHOOKS.disableAfterLadders} /> secuencias consecutivas agotadas **desactiva el
endpoint**; el procesamiento asíncrono mantiene la respuesta rápida bajo carga.

### Eliminar duplicados por id de evento

`X-BBSign-Event-Id` es estable entre reintentos y reentregas del mismo evento. La entrega es al
menos una vez, de modo que un evento puede llegar dos veces; use el id como clave de idempotencia.

### Rotación del secreto

Mientras la ventana de rotación está abierta, el encabezado lleva dos valores `v1=`.
`Webhooks.verify` acepta cualquiera de los dos, lo que le permite desplegar el nuevo secreto sin
interrupción y sin configuración adicional.

### Probar el handler

La verificación depende del tiempo: una firma con más de
<Fact of={WEBHOOKS.toleranceSeconds} unit="s" /> de antigüedad se rechaza, de modo que un fixture
fijo en una prueba unitaria deja de ser válido. Use la sobrecarga que recibe el reloj:

```java
Webhooks.verify(signature, rawBody, secret, Duration.ofSeconds(300), Instant.ofEpochSecond(1760000000L));
```

## Comprobar un archivo

`POST /api/v1/verify/file` recibe los bytes de un PDF (`application/octet-stream`, no multipart),
calcula su SHA-256 en el servidor y responde si es un documento firmado por bb-sign. Es público, no
guarda el archivo y acepta hasta <Fact of={VERIFY.fileMaxMb} unit="MB" />, con un límite de
<Fact of={RATE_LIMITS.verifyFilePerMinutePerClient} /> solicitudes por minuto por cliente.

{SDK.javaVerifyFileSendsPath.value && (
  <Aside type="caution" title="verifyDocumentFile envía la ruta, no el archivo">
    <code>client.verification().verifyDocumentFile(File)</code> serializa el <code>File</code> como
    JSON, de modo que envía la ruta del archivo entre comillas en lugar de sus bytes, y la respuesta
    nunca coincide. Es un defecto conocido del SDK. Hasta que se corrija, haga esta
    llamada por HTTP:
  </Aside>
)}

```java
HttpRequest check = HttpRequest.newBuilder(URI.create(System.getenv("BBSIGN_BASE_URL") + "/api/v1/verify/file"))
        .header("Content-Type", "application/octet-stream")
        .POST(HttpRequest.BodyPublishers.ofFile(Path.of("contract-signed.pdf")))
        .build();
HttpResponse<String> response = HttpClient.newHttpClient().send(check, HttpResponse.BodyHandlers.ofString());
if (response.statusCode() == 429) {
    String retryAfter = response.headers().firstValue("Retry-After").orElseThrow();
    // RATE_LIMITED: wait retryAfter seconds, then check again
} else {
    VerifyFileResponse result = MAPPER.readValue(response.body(), VerifyFileResponse.class);
    System.out.println(result.getMatch() + " " + result.getSha256());
}
```

Solo coinciden los PDF firmados: un original sin firmar nunca coincide. `GET /api/v1/verify`, en
cambio, comprueba el sello impreso en el código QR contra los registros de bb-sign y no lee el PDF.

## Reintentos

Las solicitudes `GET` se reintentan ante errores 5xx y timeouts de conexión, con backoff
exponencial y jitter completo, desde <Fact of={SDK.retryBaseMs} unit="ms" /> y como máximo
<Fact of={SDK.retryMaxBackoffMs} unit="ms" />.

**Un `POST` cuya respuesta no se recibió no se reintenta.** Si `createEnvelope` agota el tiempo de
espera, el resultado es desconocido: el sobre puede existir ya, y un reintento crearía un segundo
acuerdo enviado a las mismas personas. La API no usa claves de idempotencia.

Si una creación agota el tiempo de espera, **liste antes de reintentar**:

```java
try {
    client.execute(client.envelopes().createEnvelope(request));
} catch (BbSignException e) {
    if (e.statusCode() == 0) {
        // Never reached bb-sign, or the answer was lost. Check before sending again.
    }
}
```

`429` y `503` se reintentan también en `POST`, porque indican que el servidor no procesó la
solicitud. El SDK **no respeta `Retry-After`**: ante un `RATE_LIMITED`, sus reintentos llegan
antes de que se abra la ventana y fallan de nuevo. Si recibe <code>{QUOTA.httpStatusWhenExhausted.value}</code>,
espere los segundos de `Retry-After` antes de volver a llamar; esa espera queda a cargo de su código.

## Errores

Toda respuesta distinta de 2xx lanza `BbSignException`, que expone `statusCode()`. `0` indica que la
solicitud no obtuvo respuesta.

| Estado | Significado |
|---|---|
| 400 | Solicitud mal formada o con errores de validación |
| 401 | Credenciales rechazadas. El SDK renueva el token y reintenta una vez antes de reportarlo |
| 403 | Autenticado, pero esta credencial no tiene el permiso de la organización |
| 404 | El recurso no existe, o pertenece a otra organización o a un espacio de trabajo que la credencial no puede ver. No se distinguen, de forma intencional |
| 408 | La subida a la verificación por archivo superó el tiempo máximo |
| 409 | El recurso no está en un estado que permita la operación, por ejemplo enviar un sobre ya enviado o pedir el certificado de un sobre no completado |
| 410 | El archivo que se pide restaurar ya superó su plazo de conservación |
| 413 | El archivo enviado a la verificación supera el tamaño máximo |
| 429 | El servidor no procesó la solicitud: una cuota agotada (`QUOTA_EXCEEDED`), un límite de tasa (`RATE_LIMITED`) o demasiadas restauraciones en curso (`RESTORE_LIMIT_REACHED`) |
| 503 | Un servicio del que depende la operación no respondió |

{SDK.errorCarriesStatusOnly.value && (
  <p>
    <code>BbSignException</code> lleva solo el estado, no el cuerpo ni su <code>code</code>: un 429 por
    cuota y uno por límite de tasa se ven iguales. Si necesita el <code>code</code>, haga esa llamada
    por HTTP y lea el cuerpo.
  </p>
)}

Los mensajes de las excepciones nunca incluyen su secreto ni su token de acceso, aunque la
respuesta de bb-sign los contenga. [Errores](/sign/developers/errors/) incluye la tabla completa y
el cuerpo del error.

## Novedades del contrato

El SDK se genera a partir del contrato OpenAPI, de modo que una entrega actual ya tiene tipados los
campos que se agregaron desde la primera:

- `EnvelopeResponse`: `archived`, `archivedAt`, `retention` y `restoresInProgress`.
- `DocumentWithUrlsResponse`: `originalSha256`, y `original` y `signed` (`DocumentFile`, con
  `availability`, `deletesAt`, `archivesAt`, `availableUntil` y `restorable`).
- `WebhookEventData`: `evidenceStatus`, `signedDocumentsStatus`, `documents`, `documentsPath`,
  `evidenceCertificate`, `auditChainHead`, `retention` y `document`; `WebhookEventSigner.authMethod`.
- Los tipos de evento `ENVELOPE_EVIDENCE_ISSUED` y `DOCUMENT_RESTORED`.

El `CHANGELOG.md` del SDK enumera cada cambio, incluidos los que obligan a ajustar el código fuente.

## Versiones

La versión es <code><Fact of={SDK.java.version} /></code>. Las entregas posteriores conservaron ese
número aunque agregaron operaciones y campos, de modo que la versión no basta para saber qué jar
tiene. Compare el `.sha256` de su jar con el de la entrega más reciente que le enviamos.

## Garantías de seguridad

- **Credenciales fuera de los logs.** El SDK no incluye interceptor de logging ni punto para
  instalar uno. Evite agregar por su cuenta el `HttpLoggingInterceptor` de okhttp en nivel `BODY`:
  imprime el encabezado `Authorization` y el cuerpo del formulario del token tal cual.
- **TLS siempre verificado.** La verificación de certificados no se puede desactivar.
- **Escrituras sin duplicados.** Una escritura con resultado desconocido no se reintenta (ver
  [Reintentos](#reintentos)).

## Compilar desde el código fuente

```bash
cd sdk-java
mvn verify          # regenerates the client, compiles, runs the tests
./verify.sh         # the CI gate: drift, Jackson-not-Gson, plugin survival
mvn package         # writes the handover artifact to target/handover/
```

El cliente en `src/main/java/co/binarybridges/sign/sdk/generated/` es **código generado y
versionado**: regenérelo en lugar de editarlo. Se versiona para que cada cambio en la
especificación aparezca como un diff revisable.
