## Instalación

Recibiste cuatro archivos: el jar, su pom, un `.sha256` y esta guía. Instala el jar en tu repositorio
local de Maven y luego decláralo como dependencia.

<Steps>
1. Comprueba que recibiste lo que enviamos:

   ```bash
   shasum -a 256 -c bb-sign-sdk-java-0.1.0-SNAPSHOT.jar.sha256
   ```

2. Instálalo. **`-DpomFile` es obligatorio:**

   ```bash
   mvn install:install-file \
     -Dfile=bb-sign-sdk-java-0.1.0-SNAPSHOT.jar \
     -DpomFile=bb-sign-sdk-java-0.1.0-SNAPSHOT.pom
   ```

3. Decláralo como dependencia:

   ```xml
   <dependency>
     <groupId>co.binarybridges.sign</groupId>
     <artifactId>bb-sign-sdk-java</artifactId>
     <version>0.1.0-SNAPSHOT</version>
   </dependency>
   ```
</Steps>

<Aside type="caution" title="No omitas -DpomFile">
  Sin él, Maven sintetiza un pom que no declara dependencias. La instalación tiene éxito y tu build
  tiene éxito, y después tu primera llamada a la API falla en tiempo de ejecución con
  `NoClassDefFoundError` para una clase de Retrofit o de okhttp, muy lejos de la causa. El pom es lo
  que trae okhttp, Retrofit y Jackson. Si ves ese error, reinstala con `-DpomFile`.
</Aside>

### Lo que esto asume

**Tu build puede alcanzar Maven Central.** Este es un jar simple, no un jar shaded, así que tu build
resuelve okhttp, Retrofit y Jackson por su cuenta y, lo que importa, los deduplica contra las
versiones que ya tienes. Jackson en particular ya está presente en la mayoría de los servicios Java,
y empaquetar una segunda copia causa conflictos mucho más difíciles de diagnosticar que una
dependencia faltante.

Si tu build no puede alcanzar Central, avísanos antes de empezar. Un build shaded es posible; es un
artefacto distinto y preferimos producirlo antes de que descubras el problema a mitad de la
integración.

## Inicio rápido

Todo lo que sigue es un solo archivo. Las credenciales salen de **Configuración**, pestaña
**Credenciales de API** en bb-sign; el secreto se muestra una sola vez, al crearlo.

```java
import co.binarybridges.sign.sdk.BbSignClient;
import co.binarybridges.sign.sdk.generated.model.*;
import java.time.OffsetDateTime;
import java.util.List;

try (BbSignClient client = BbSignClient.builder()
        .baseUrl(System.getenv("BBSIGN_BASE_URL"))
        .tokenUrl(System.getenv("BBSIGN_TOKEN_URL"))
        .clientCredentials(System.getenv("BBSIGN_CLIENT_ID"), System.getenv("BBSIGN_CLIENT_SECRET"))
        .build()) {

    CreateEnvelopeRequest request = new CreateEnvelopeRequest()
            .title("Q3 Agreement")
            .otpRequired(false)
            .expiresAt(OffsetDateTime.now().plusHours(72))
            .signers(List.of(new CreateSignerSpec()
                    .email("signer@example.com")
                    .name("A Signer")
                    .signOrder(1)));

    EnvelopeResponse envelope = client.execute(client.envelopes().createEnvelope(request));
    System.out.println("Created " + envelope.getId());
}
```

Lee las credenciales del entorno, no del código fuente. El secreto no se puede recuperar después de
crearlo: se guarda solo en Keycloak y bb-sign no conserva copia. Si se pierde, rótalo, lo que
invalida el anterior **de inmediato**. El cliente expone `envelopes()`, `documents()` y
`verification()`.

### Listar, una página a la vez

```java
client.eachPage(
        page -> client.envelopes().listEnvelopes(page, 50, null, null, null, null, null, null),
        PagedEnvelopeResponse::getContent)
    .forEach(envelope -> System.out.println(envelope.getTitle()));
```

Las páginas se obtienen de forma perezosa a medida que iteras, así que contar cincuenta mil sobres
no pone cincuenta mil sobres en memoria.

## Verificar un webhook

**Lee esta sección antes de escribir el handler.** El fallo de integración más común no está en este
SDK; está en cómo el cuerpo llega hasta él.

```java
import co.binarybridges.sign.sdk.Webhooks;

@PostMapping("/webhooks/bb-sign")
public ResponseEntity<Void> receive(
        @RequestHeader("X-BBSign-Signature") String signature,
        @RequestBody byte[] rawBody) {                 // byte[], NOT a DTO

    if (!Webhooks.verify(signature, rawBody, System.getenv("BBSIGN_WEBHOOK_SECRET"))) {
        return ResponseEntity.status(401).build();
    }

    WebhookEvent event = new ObjectMapper().readValue(rawBody, WebhookEvent.class);
    switch (event.getType()) {
        case "envelope.completed" -> onCompleted(event.getData().getEnvelope());
        case "signer.signed"      -> onSigned(event.getData().getSigner());
        default                   -> { /* ignore unknown types: more will be added */ }
    }
    return ResponseEntity.ok().build();
}
```

### El raw body no es un detalle

La firma cubre **los bytes exactos que viajan por la red**. Declarar el parámetro como un DTO hace que
Spring parsee el JSON y te entregue un objeto; volver a serializar ese objeto produce bytes distintos
(cambian el orden de las claves y los espacios) y la verificación falla por una razón que no puedes
ver en un depurador, porque el objeto se ve correcto.

- **Spring MVC**: `@RequestBody byte[]` o `@RequestBody String`, o un `ContentCachingRequestWrapper`
  si además necesitas la forma parseada.
- **Jakarta Servlet**: lee `request.getInputStream()` una sola vez, antes de que cualquier otra cosa
  lo toque.

El SDK recibe `byte[]` en lugar de `String` a propósito: el tipo hace que esto sea difícil de hacer
mal.

### Responde rápido, trabaja después

Devuelve 2xx tan pronto la firma sea válida y haz el trabajo de forma asíncrona. bb-sign reintenta
con una escalera que abarca aproximadamente
<Fact of={WEBHOOKS.retryLadderHoursApprox} unit="horas" />, y tras
<Fact of={WEBHOOKS.disableAfterLadders} /> escaleras consecutivas agotadas **deshabilita tu
endpoint**; un handler que haga treinta segundos de trabajo en línea lo disparará bajo carga.

### Deduplica por el id del evento

`X-BBSign-Event-Id` es estable entre reintentos e idéntico en las reentregas del mismo evento. La
entrega es al menos una vez, así que el mismo evento puede llegar dos veces; trata el id como clave
de idempotencia.

### Durante una rotación del secreto

El header lleva dos valores `v1=` mientras la ventana de rotación está abierta. `Webhooks.verify`
acepta cualquiera de los dos, que es lo que te permite redesplegar sin interrupción. No hay nada que
configurar.

### Probar tu handler

La verificación depende del tiempo: una firma con más de
<Fact of={WEBHOOKS.toleranceSeconds} unit="s" /> de antigüedad se rechaza, así que un fixture fijo
en una prueba unitaria falla mañana. Usa la sobrecarga que recibe el reloj:

```java
Webhooks.verify(signature, rawBody, secret, Duration.ofSeconds(300), Instant.ofEpochSecond(1760000000L));
```

## Reintentos, y lo único que este SDK no hará por ti

Las solicitudes `GET` se reintentan ante 5xx y ante timeouts de conexión, con backoff exponencial y
jitter completo.

**Un `POST` cuya respuesta nunca se vio no se reintenta jamás.** Si `createEnvelope` agota el tiempo
de espera, el resultado es genuinamente desconocido: el sobre puede existir. Reintentar crearía un
segundo, y estos son acuerdos legales enviados a personas reales. La API no tiene clave de
idempotencia, así que no hay forma de hacerlo seguro.

Si una creación agota el tiempo de espera, **lista antes de reintentar**:

```java
try {
    client.execute(client.envelopes().createEnvelope(request));
} catch (BbSignException e) {
    if (e.statusCode() == 0) {
        // Never reached bb-sign, or the answer was lost. Check before sending again.
    }
}
```

`429` y `503` **sí** se reintentan, incluso para `POST`: significan que el servidor explícitamente no
procesó la solicitud.

## Errores

Toda respuesta que no sea 2xx lanza `BbSignException`, que lleva `statusCode()`. `0` significa que la
solicitud nunca obtuvo respuesta.

| Estado | Significado |
|---|---|
| 400 | Mal formada o falló la validación |
| 401 | Credenciales rechazadas. El SDK renueva el token y reintenta una vez antes de reportarlo |
| 403 | Autenticado, pero esta credencial no tiene el permiso de la organización |
| 404 | El recurso no existe, o pertenece a otra organización o a un espacio de trabajo que no puedes ver. Indistinguible a propósito |
| 409 | No está en un estado que permita esto, por ejemplo enviar un sobre ya enviado |
| 429 | Una cuota de la organización está agotada |

Los mensajes de las excepciones nunca contienen tu secreto ni tu token de acceso, incluso cuando la
respuesta de bb-sign sí los contiene. [Errores](/sign/developers/errors/) tiene la tabla completa y el
cuerpo del error.

## Lo que este SDK no hará

- **Registrar tus credenciales en el log.** No hay interceptor de logging ni hook para instalar uno.
  El `HttpLoggingInterceptor` de okhttp en nivel `BODY` imprime el header `Authorization` y el cuerpo
  del formulario del token tal cual; actívalo por tu cuenta y tu secreto queda en tu agregador de
  logs para siempre.
- **Dejarte desactivar la verificación TLS.** No hay bandera para eso. Se activa para un certificado
  de staging y nunca se vuelve a desactivar.
- **Reintentar una escritura con resultado desconocido.** Ver arriba.

## Compilar desde el código fuente

```bash
cd sdk-java
mvn verify          # regenerates the client, compiles, runs the tests
./verify.sh         # the CI gate: drift, Jackson-not-Gson, plugin survival
mvn package         # writes the handover artifact to target/handover/
```

El cliente bajo `src/main/java/co/binarybridges/sign/sdk/generated/` es **generado y versionado**.
Nunca lo edites; regenéralo. Está versionado en lugar de ignorado para que un cambio en la
especificación aparezca como un diff revisable en vez de colarse en silencio en el siguiente build.
